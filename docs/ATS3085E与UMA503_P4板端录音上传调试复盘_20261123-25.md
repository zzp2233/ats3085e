## 2. 硬件接线和新人基础

| 信号 | ATS 主机 | UMA503 从机 | 验证位置 |
|---|---|---|---|
| CS | GPIO57 | PCM_SYNC 焊盘 31 | 从机端低有效，与每次完整时钟窗口对应 |
| SCK | GPIO58 | PCM_CLK 焊盘 30 | Mode 3，空闲高，4 MHz 时数 4,096 个上升沿 |
| MOSI | GPIO60 | PCM_DIN 焊盘 32 | 主机发送方向 |
| MISO | GPIO59 | PCM_DOUT 焊盘 33 | 从机回包方向，能否稳定采到合法 CA 方向字节及 CRC |
| READY | GPIO61 | GPIO50 / I2C_SDA 焊盘 66 | 503 → ATS，1.8 V。启动信标与业务许可按阶段解释 |
| GND | 地 | 地 | 两板和分析仪共地 |

COM4 是 ATS Shell，2,000,000 / 8N1。COM6 保留 UMA 开机和业务日志。先对照焊盘、探头和解码通道。11-25 09:30 与 09:43 的采集说明，探头通道映射不准可把成功的串口交易误判为线路异常，也可漏掉真正的失步。对正式比较保持接线固定，摆动后的结果另记。

STM32 11-2 的 `MySPI_Start()`、`MySPI_SwapByte()`、`MySPI_Stop()` 可以用来理解一笔 CS 内的全双工交换。

这里 ATS 定长 TX DMA 给 512 B 的时钟，UMA 预装 MISO；主机等 READY 才可开下一对。

像 STM32 的 TXE 与 BSY 一样，DMA 已写完、SPI 线端结束、从机业务处理完成各有判据。

以 W25Q64 为例，地址决定读哪段内容；P4 则由服务端 offset/length 决定读取哪段录音，并额外用 init 与 complete 确认远端状态。

## 4. 逐项 BUG 复盘

### 先学会用三份证据找到首错

一次上传同时经过 ATS 命令线程、UMA SPI 接收任务、UMA 网络 worker 与远端。

先给这次运行记下固件组合、启动时间、同一文件 ID、当时阶段及两端事务计数。

跨设备时间戳有采集偏差时，用首笔 CS、同一请求号和帧序列做对齐。优先保存首错、当前缓冲地址和剩余量。STOP 后的清理快照只用来检查资源是否释放。

| 第一眼看到的现象 | 花一分钟先问什么 | 读哪项 |
|---|---|---|
| HTTP 为 0 或响应没收到 | 是否发了请求、是否见到从机 STOP、最后一个成功阶段是什么？ | 01、07、10 |
| HTTP 401 或校验分片失败 | 能否从线上还原真实请求？是响应状态还是本地解释失败？ | 01a、06 |
| 从机重启、ATS 突然停机 | 哪个处理器、哪个线程的栈报错？ | 03、05 |
| CRC 对但仍报非法槽，或 MISO 发生移位 | CRC 覆盖哪里？线端与两端内存各显示什么？ | 02、04、04a、12 |
| 主机一直等 READY | 前一条是开机握手、普通数据还是网络 QUIET？数过时钟吗？ | 08、10、11、13 |
| 断网后失败或重新下发 | 重试预算是否覆盖入网，原文件 ID 是否保持？ | 07、09 |

**从 STM32 过渡到项目。**

把 `MySPI_SwapByte()` 拆成三步：CPU 或 DMA 送数据给外设，移位器用时钟交换，另一方向的数据进入缓冲。TXE、RXNE、BSY 对应不同观察时刻。

项目再向上加三层：DMA 双槽所有权、SPI 应用命令与回执、HTTPS 业务会话。

某个下层成功只允许进入下一层。这样才能理解为什么一整笔 512 B 合格，应用仍可能拒绝回执，或者为什么 HTTP 200 已出现，业务仍要用 init 对账。



### 01｜23 日首轮 init 已发送却没有响应

**现象。** 主机读回内置 265,113 B 录音，503 的 DNS/TCP/TLS 已通过，281 B 的 init 正文送到 worker，但没有 HTTP 响应。

**目标与定位。** 目标是还原“最后确认的动作”和“第一个没有证据的动作”。把一次 init 拆成 SOURCE 校验、请求构造、SPI 元数据、网络连接、TLS 握手、请求体发送、收 HTTP 和主机响应校验。读日志先列步骤再圈停点。

**根因与排查。** 此时服务端可能已处理请求。缺少响应时能确定的是结果未知，不能把后续 PUT 或 complete 算在内。沿 TLS、组发送和 FINISH 分阶段取证。

**改动与理由。** 保留文件身份，增加阶段输出和进度查询。下一次使用原 ID 重新 init，让服务端状态决定下一步。

**验证与边界。** 后续有同 ID 查询及完整闭环。23 日首轮仍记失败。时间戳修订在 24 日另行验收，不能只凭初次超时断言是签名。

#### 怎样复查这个案例

| 2026-11-23 首轮观测 | 能确认到哪里 |
|---|---|
| SOURCE code=0，265,113 B | NOR 内置资源可读并与输入摘要一致 |
| 503 收到 281 B JSON，DNS/TCP/TLS 均成功 | 网络请求已经走到连接与正文路径 |
| QUIET end status=0 ticks=1839 | 首个工作阶段完成，约 9.195 s 的量级 |
| 缺 HTTP 响应，未见录音 PUT 或 complete | init 在服务端的执行结果未知，当前闭环失败 |

**怎么读代码。** 从 ATS `p4_upload.c` 的 `signed_post()` 跟到 `spi_link_p4.h` 的 `p4_spi_request()`，再找 UMA `spi_link_file_slave.h` 的组消费、`spi_link_https.c` 的响应读取。用日志区分 TLS 库返回、HTTP 状态和板端 SPI 结果。仅有 TLS ready 说明握手完成。接下来要完整收取 HTTP 并解释业务字段，才可决定是否取待传范围。

**动手练习。** 把“发送正文成功”“服务端确认已处理”“主机取得完整响应”分别写在纸上。假设最后一步掉线，给本地任务记失败或未知，保留原 ID。复测先读服务端的已传字节、连续进度和 pendingParts，再决定下一动作。若换新 ID，就丢失这次查询原结果的机会。

### 01a｜HTTP 401 的根因要从实际发送的字节找

**现象。** 11 月 24 日 11:01 能完整取回 HTTP 401。分析仪 37 笔与双端计数一致，实际请求头含 `X-Device-Timestamp: lu`。

**目标与定位。** 确定 401 来自坏时间戳、签名构造错误还是其他鉴权条件。先确认返回确为 HTTP 401，而非主机把线端超时解释成失败；局部日志 `complete=1` 此处表示响应取完。

**根因与排查。** 原 `%llu` 在该 ARM newlib-nano 配置下没有生成十进制数。用与目标相同工具链和 `nano.specs` 离线复现 `lu`，而原先使用完整 newlib 的模型没有发现差异。按线端实际正文与头重算签名一致，问题位于用来签名和发送的时间戳字符串。检查输入、格式化产物、canonical 字节、线上请求，再判断是否需要检查凭据。

**改动。** `p4_upload.c` 的 `prepare_post()` 用 `snprintf(..., "%u000", (unsigned int)w->utc)` 生成毫秒字段，并检查返回长度。签名和请求头共用这一字符串。

**为什么这样改。** 输入只有整数秒精度。以十进制形式后接三个零与乘 1,000 等值，避开目标库的 64 位格式化差异。整条业务签名计算仍围绕同一份正文及请求头。

**验证与边界。** 修复前 nano 测试复现非法值；TIMEFIX 构建验证了新格式及资源封装。后续实际 init 成功才证明端到端跨过该门槛。401 仍可能有其他来源，后续不能用一个字符串故障解释所有 HTTP 拒绝。依据为 `P4_1103分析与时间戳修复_20261124.md`、`1103.atkdl` 的脱敏结论。练习在本机分别用完整 libc 和目标 libc 跑同一段格式化，再比串口和线端字节。

### 02｜重复测试有时成功，后续阶段又超时

**现象。** 24 日 11:37、14:11～15:21 多次在配对与对账附近失败。14:27 发现 CS 短脉冲记录，14:33 摆动接线后 PUT 返回 200、后续对账仍失败。15:26 低速完整闭环通过。

**目标与定位。** 在纠结线、外设还是软件前，先找“哪一笔最早失去一致性”。时钟看分析仪原始数据，事务按 CS 有效区划分。50 MHz 每点 20 ns，4 MHz 的周期应常见 12/13 个采样点。把同槽同类应答作参照，跨采样页按绝对采样号拼接。不要拿不同请求号的整帧直接做移位推断。

**根因与排查。** 分开检查采样时间、CS、配对 witness 和已完成笔数。某轮低速或换线成功仅支持该轮条件。部分采集不能还原首错。

**改动与理由。** 用约 2.286 MHz 的可达分频与 4 MHz 做对照，保留主从日志和完整波形，再回到 4 MHz 复跑。线路操作逐次记录。

**验证与边界。** 4 MHz 16:15～16:29 前四轮通过，第五轮 INIT 超时。不能用前四轮覆盖失败轮。

#### 怎样复查这个案例

| 真实观测 | 正确读法 |
|---|---|
| 14:27 的 21 笔 MOSI CRC 全对，MISO 第 20、21 笔坏 | 查 TLS/QUIET 后第一对。第 20 笔首差 bit 2636，尾段存在相对参考延后 98 位的匹配 |
| 同轮帧内 230 个 CS 单点高，CRC 正常的第 15 笔也有 136 个 | 单采样点是数字采集事实。脉宽、门限和 503 是否实际看到它需要独立验证 |
| 14:33 的 663 笔均有 4,096 个采样沿，MOSI CRC 全过，PUT 200 | 失败落在对账。第 662 笔 MISO 前 372 位对，后段可匹配提前 2 位；完整时钟数量仍可能伴随内容失步 |

**为什么降速只做对照。** 固定线、版本和请求范围后只变 SCK，便于看故障是否随服务时间变化。ATS HOSC 档位使约 2.286 MHz 可实现，分析仪解码和寄存器读回应一致。降速通过随后回到 4 MHz 仍可能失败，这要求保留首错数据而非直接结束排查。

**复测步骤。** 固定探头，选从机侧测点并共地，每轮记录通道、阈值、采样率和有效覆盖。逐笔列 CS、上升沿数、MOSI/MISO CRC、首差位置和软件计数。需要确定模拟尖峰或阈值时，在接收端另用示波器。把好帧、坏帧的相同测量指标并排比较。依据为 P4 归档 1427、1433、1629 记录。

### 03｜503 网络状态任务出现栈告警与复位

**现象。** 24 日 15:32 首轮业务成功，第二轮网络状态任务报栈告警并复位。从任务名和镜像反汇编定位到 `oc_net_status_`。

**目标与定位。** 沿 `线程名 → 映像 → 创建调用 → 分配和登记参数` 找到可证实的错误。先分清 OpenCPU 应用和 CP 预编译镜像，再检查是否是业务 worker 自己的栈不足。

**根因与排查。** 该 CP 任务分配 4,096 B，却登记为 1,024 B。HTTPS worker 是另一条任务路径。缺少首错完整内存转储，无法完全排除其他内存破坏。

**改动与理由。** NETSTACK 在匹配输入镜像的外部副本里把登记值修到 4,096 B。脚本验证输入哈希和目标位置，避免修改不匹配固件及 SDK 原预编译件。

**验证与边界。** 配套包后续多轮闭环。CP 修订是绑定版本的历史交付动作，源码提交不能自动复现该镜像。更换 SDK 要重查。

#### 怎样复查这个案例

| 字段 | 修复前 | NETSTACK 镜像 |
|---|---:|---:|
| `oc_net_status_` 已分配空间 | 4,096 B | 4,096 B |
| 传给任务创建的栈大小 | 1,024 B | 4,096 B |
| 诊断动作 | 15:32 第二轮网络状态任务报警 | 保留原镜像，核对哈希后只改外部副本目标值 |

**新人补课。** 裸机上常看一个主栈，RTOS 每个任务有自己的栈。预留了一段 RAM 后，任务创建登记的边界决定该段怎样被使用。一个任务在 TLS 后报错不能推出 TLS 的大对象都进了它的栈。先拿任务名和创建参数说话。复测在相同配套包连续执行多轮，查相同线程是否再出现告警、重启或 WDT。镜像修订仅适用核对过的 CP 版本。依据为 `P4_NETSTACK_修复与烧录_20261124.md`。

### 04｜MOSI 全对，MISO 连续提前两字节

**现象。** 24 日 16:35，同 ID 重试卡设备信息，还没进入 HTTPS。2,980 帧 MOSI CRC 全对，MISO 每帧表现为 `07 00 … CA 01`。每帧 4,096 个时钟。

**目标与定位。** 用线端和内存两套证据区分解析、采样和数据来源。第一步核对正常响应头在 offset 0 的 `CA 01`。第二步数出 2,980 笔线端与从机 blocks 增量闭合。第三步只离线验证旋转前后的头、内容与 CRC。旋转后的数学匹配不会告诉你是哪个寄存器或物理边沿先出问题。

**根因与排查。** 只在离线分析把末尾两字节转回开头，2,980 帧 CRC 恢复，证明偏移已发生在线端。应用 ABORT 无法使链路复位。首次位移的物理诱因仍待证实。

**改动与理由。** RESYNC / RXRECOVER 收紧坏帧与配对边界检查，在可辨认条件下受控停止并重建 SSP/DMA，验证 cookie、事务号和回包。恢复并不续跑当前未确定业务。

**验证与边界。** 17:24～17:31 四次普通新上传通过，前三次完整波形各 710 笔，重建录音一致。正常回归没有触发恢复分支。运行中注入验收见案例 12。

#### 怎样复查这个案例

**为什么这样改。** STM32 中 DMA TC 只表示指定搬运完成。此处描述符、外设 FIFO 与移位器还可能各存不同阶段的数据。复位恢复必须同时明确双方的槽位置，清掉上一事务残留，并证明新 tid、请求号、cookie 与 CRC 一起匹配。应用 ABORT 只能改变协议会话，无法保证外设重新按字节对齐。查 ATS `sfile_resync()` 和 UMA `spi_link_dma_circular.h` 的异常检测与重装，再回到业务状态机。

**复测步骤。** 先用正常包完成新 ID，再单独注入可控坏对。对于现场坏帧，应保持原始内容及首错，不在接收时把末尾数据移回开头后接受。重建成功也以当前业务 FAIL、下一次同 ID 可安全查询为验收，详见案例 12。

### 04a｜头 CRC 正确，完整缓冲仍可能在中途失步

**现象。** 11 月 24 日 21:59 的失败交易中，线上 30 笔完整帧双向 CRC 都正确，但 UMA 的 slot0 与对应第 24 笔线端数据从 bit 673（offset 84 内）开始出现差异。该笔是 `len=0` 的 QUERY。

**目标与定位。** 比较同笔线端和从机实际内存，而非只比两个端点的 CRC 总计。先按命令头、槽序号、相邻帧和时钟数量锁定对应关系。

**根因与排查。** 对线端数据离线补入一个零位并丢弃末尾一位即可匹配完整 slot0。在连续零区 bit 668～673 内，准确插入位置无法区分。由于 QUERY 的有效载荷为零，CRC 仅检查头；尾部 witness 另查，所以二者可分别成功和失败。恢复期间另见两个 CS 高时的孤立上升沿，它们晚于故障。

**改动。** 继续使用配对 witness、严格 CRC 和有限重同步。抓包时同时保存线端字节、首错 DMA 槽及命令长度。

**为什么这样改。** 对已发生的位偏移进行离线对齐有助于判断差异形态。产品接收端仍需拒绝坏槽，防止把上一响应或错误阶段误交给 HTTPS。

**验证与边界。** 本轮从机 RX RECOVERY 和双端 RESYNC 成功，当前 INIT 报 -1002、RESULT FAIL，没有 PUT。50 MHz 在探测点未看到额外完整帧内脉冲，仍无法排除更窄的模拟扰动或内部采样问题。依据为 `P4_2159第二笔init单bit失步与恢复结果_20261124.md`。

### 05｜主机在发 init 之前耗尽 shell_uart 的 2 KiB 栈

**现象。** 17:51 发 128 KiB 提示参数，TRNG 成功后栈 2,048/2,048 B，Zephyr FATAL ERROR 2。UMA 只见 7 块设备查询等事务，未见 START_HTTP/META/DATA。

**目标与定位。** 查同一次 ATS fatal 的线程名、SP、实际栈大小和对应 ELF。将观察时间排序为“设备查询成功 → SE_TRNG ret=0 → ATS fatal → 无 START_HTTP”。当另一块板还在打印健康日志时，先查本地而不是重刷双方。

**根因与排查。** 实际 ELF 显示检查位置及上传到 SPI open/日志的栈链。检测函数位置本身不能指认首次覆盖指令。这个故障与 503 的 CP 任务不同。

**改动与理由。** STACKFIX 减少热路径栈负担，用保留栈余量观察后续实机。构建加栈使用量输出，复验使用本轮实际 ELF。

**验证与边界。** 18:03 已进入真实 init，未复现该次崩溃。19:07 记录 452 B 未使用栈，仅代表当轮路径。

#### 怎样复查这个案例

**为什么要改栈布局。** 函数参数、局部数组、保存寄存器和嵌套调用都会用同一 Shell 栈。把一条路径的工作区拆离深调用后，编译器栈报告可以帮助找较大函数。报告的单函数帧大小仍需结合调用链和中断现场。源码从 `shell_p4upload()`、`p4_upload_run()`、`prepare_post()`、`p4_spi_request()` 跟到 SPI open，再对照链接符号和 `P4 STACK ... unused=`。不要用扩大任务栈掩盖尚未查明的覆盖。

**改动与取舍。** 作业上下文随工作区从堆分配。SPI 新增指针入口 `sfile_run_context()`，避免在栈上复制较大上下文；`prepare_post()` 和分片检查的临时帧不内联到深层调用。空间不足时在发请求前失败，退出清零释放。Shell 栈继续保持 2,048 B，历史构建比较中相关应用层栈帧合计 1,008 → 520 B，设备查询适配 336 → 32 B。这个 488 B 差值只覆盖列出的应用层，完整调用链仍含驱动、格式化和异常上下文。

**复测。** 使用带录音资源的完整 FW，保持同一 128 KiB 提示参数。期待先越过原 fault 点进入 init，再另行处理业务分片响应。记录空闲栈最小观测值；网络错误路径、重复调用和最大响应也应各走一次。依据为 1752/1803 阶段报告。

### 06｜128 KiB 分片提示已发送，服务端却返回一整片

**现象。** 18:03 init HTTP 200、业务 00000，申请 partSize 131,072 B，固件 `PUT_PREPARE -1004`，尚未 PUT。

**目标与定位。** 核对“请求分片提示”“响应中的真实范围”“文件可读长度”三列。18:03 已收到 610 B 完整 init 响应、业务 00000、已传和连续进度为 0。问题发生在 ATS 的 `put_spec()`，进入 HTTP PUT 之前。

**根因与排查。** 本地把分片提示当作实际布局限制，服务端响应可以给整个 265,113 B 的单片。对照 ZS302A 的 range 处理与后端返回。

**改动与理由。** REFERENCE 按 pendingParts 的 offset/length 读取，校验范围与响应完整性；相同身份用于对账。避免从本地提示值推断待传偏移。

**验证与边界。** 18:52 响应一片、长度 265,113 B，四次 HTTP 200、SYNC_SUCCESS。这个用例证明范围适配，未证明真实多片或非零偏移已上板验收。

#### 怎样复查这个案例

| 边界 | 本轮例子 | 验收含义 |
|---|---|---|
| 请求提示 | 128 KiB = 131,072 B | 请求上的偏好 |
| 服务端返回 | offset=0、length=265,113 | 本轮实际读入并送出的范围 |
| 文件长度 | 265,113 B | 先检查 `offset <= size`，再检查 `length <= size - offset`，避免相加溢出 |

**为什么这样改。** 像按 W25Q64 地址读取数据一样，偏移与长度决定字节范围。上层 partSize 不应参与猜测下一片偏移。如果服务端给非零偏移，数据源必须从该偏移读，不可从文件头重发。分片完全与否最终看 `pendingParts` 和远端连续进度。

**复测。** 用原提示值而新测试身份重跑，先验响应给出 265,113，再检查 PART_RANGE、PUT Content-Length、MOSI 数据以及后端对账数。18:52 该流程约 45.14 s 并通过。下一关是超过一片、非零偏移和最后短片的真机测试。依据为 1803 与 1852 报告。

### 07｜请求送达和收到成功回包必须分别确认

**现象。** 19:07 both-lost 故意丢弃成功的 PUT 和 complete 响应。19:13～19:24 另测未发送 PUT、未发送 complete、模拟 PUT 403 和 init 503。

**目标与定位。** 为每个写请求标出三种状态：明确未发、明确获得结果、已送出但响应未知。之后只依据状态和远端当前进度推进。

**根因与排查。** 发送前失败、返回明示错误和响应不可见会留下不同的远端状态。只从本地返回码决定是否重传，会重复发送或提前标记已同步。

**改动与理由。** 业务状态机用相同 ID 再 init，根据待片、连续字节和同一会话 ID 决定补传、complete 或直接结束。诊断分支显式注入，避免拿模拟状态当服务器实报。

**验证与边界。** 19:07 首次五个 HTTP 请求均真实返回 200，两个注入点触发后自动对账。第二次同 ID 只有一次 init。注入结果覆盖该状态机分支，真实断线见案例 09。

#### 怎样复查这个案例

| 诊断输入 | 必须看见的下一步 | 不能由单个日志推出的结论 |
|---|---|---|
| PUT 成功回包被丢弃 | 同 ID init，服务端确认完整后跳过已传片 | 看到本地失败就需要重新 PUT |
| complete 成功回包被丢弃 | 同 ID init，确认同会话 SYNC_SUCCESS | 本地没回包就代表服务器没提交 |
| 请求在发送前被拦 | 查询后仍需要相应动作才补发 | 仅凭已触发注入就算正常网络覆盖 |
| 403 或 init 503 模拟 | 有界等待和重查，按服务端刷新结果继续 | 对象真实拒绝或后端现场故障已经实测 |

**读代码和判据。** 从 `p4_fault.h` 看注入位，再沿 `p4_upload_run()` 的身份检查和 progress 追踪。19:07 首轮是 `init → PUT → init → complete → init`，58.632 s。第二轮仅一次 init，9.646 s。armed 与 fired 用来证明所期待的注入点实际执行。第二轮已是 SYNC_SUCCESS，不执行数据操作，fired=0 符合预期。冷启动持久化、重启跨会话和真实服务端 403 应单列。依据为 1907、1913、1917、1921、1924 报告。

### 08｜503 单独重启后，旧 READY 状态让主机失去握手

**现象。** 19:29 UMA 单独重启后主机等 READY 超时；11-25 10:06 启动首帧出现 MISO 两字节错位，11:04 另一次失败窗口没有 CLK。

**目标与定位。** 用三个现场判断主机卡在哪里。若 CS/SCK 全静止，核对 READY 观察、GPIO 状态及旧会话锁定。若首笔有完整 4,096 个上升沿但 MISO 头转位，查启动预装和读取。若业务已开始，再看正常 token 与半帧退出。10:10 的 `app spi2soak show` 仅回读 10:06 同一 tid/frame 的首错，不能计作再现一次。把两次输出的重叠字节核对一致后补回截断行，完整 512 B 与线上均为 `13 00 … CA 01`。这比单看主机读错更有说服力。

**根因与排查。** READY 高低本身只反映当前电平，旧会话不能据此认领新令牌。先区分完全未打钟、首帧前置错误、握手响应损坏。

**改动与理由。** BOOTSYNC / BOOTRECOVER 让从机用约 40 ms 的连续边沿宣告启动，主控先无时钟观察，再用严格 CRC、cookie 和配套响应完成启动握手。错帧后只在明确条件下有界重建，当前业务报失败。

**验证与边界。** 19:54 有重启恢复业务成功日志，MISO 采集受限。25 日 15:03 的无时钟重试有专门证据，见案例 13。

#### 怎样复查这个案例

**为什么用信标加握手。** STM32 裸机直接看一根 GPIO 时，常把高当作 READY。这里用翻转表示一次许可，会话两边各自记住一位历史。单独复位后，即使线是高，也不知道它是旧许可还是新从机初值。规律边沿让主机在不打钟时先识别启动窗口，最终仍用 `sfile_boot_attempt()` 的 CRC/cookie 证明收到的是新启动回复。阅读 ATS `spi_link_ready.h`、`spi_link_file_host.h` 及 UMA 的 BOOT 帧预装和启动回收路径。

**复测。** 先两端同步开机保留正常基线，再分别复现 ATS 先启动或 503 单独重启。保持同一个已完成 ID，验收只查进度。正常静默会话不会每约 40 ms 周期性翻转；单次边沿和持续信标分别记。依据为 1929、1954、1006、1010、1104 记录。

### 09｜无线中断持续时间超过原重试预算

**现象。** 20:18/20:20 射频测试中，网络很快失败，1/2/4 s 的有限重试在约 12 s 射频中断结束前耗尽。

**目标与定位。** 从 `射频关闭 → 网络返回错误 → 注册恢复 → 重新 init → 明确结果` 列时间轴。原间隔 1/2/4 s 总等待名义约 7 s，实际失败比重新注册早约 4 s。证明这一点需要同时保留两端串口、断网控制入口和注册状态，不能只看 HTTP=0。

**根因与排查。** 旧等待窗口与实际重新注册时间不匹配。SPI 协议错位、DNS 未就绪和远端进度未知处理不同。

**改动与理由。** RADIO 明确测试关网与恢复，NETWAIT 在整体期限内等待后同 ID 重查；SPI 已挂起的故障不进入普通网络重试。

**验证与边界。** 20:38 途中断网用例同一命令内重新 init、重传并 complete。上传前无网用例后遇 SPI 失败，20:53 单独同 ID 对账闭合。20:38 MISO 采集全 FF，不作双向波形通过证据。

#### 怎样复查这个案例

**为什么这样改。** 业务等待期限覆盖数次实际连接和退避，该预算由同一开始时刻扣减。重启网络、等待可用后要查同 ID，接到已传进度再决定补片。SPI 错位、响应 JSON 无效和已知业务拒绝走各自分支，不能放进相同循环。源码读 UMA `spi_link_radio_test.c` 和 ATS `p4_upload.c` 的 `request_error()`、`network_expired()`。

**复测。** 复现上传前断网与 PUT 中途断网，以射频控制、TLS/网络错误、复网和最终 HTTP/业务结果取证。20:38 的两轮应分开。第一轮 complete 附近出现 SPI 错误，需要同 ID 处理；第二轮一条命令自动恢复，无重启或手工续发。若波形 MISO 全 FF 而日志完整，只认可相应串口证据并补查探头，不以此宣称双向帧全对。

### 10｜空闲及网络 QUIET 之后仍可能出现另一种失步

**现象。** 25 日 11:21 十秒空闲、五秒 QUIET 离线通过；11:26 真实 PUT 200 后紧接 init，SPI 失步 STOP，complete 未执行。

**目标与定位。** 只问“真正首错是哪一层”。11:26 的顺序为 `11:25:56 PUT 200 → 11:26:06.214 RECEIVE -216 → 11:26:06.674 STOP → 11:26:32.345 主机 -116`。因此主机看到 READY 超时，是从机先停之后的表现。此时 complete 还未执行。

**根因与排查。** 前一轮诊断所经状态不覆盖真实网络任务的每次交接，需保留 ACK、witness 和首错状态。PUT 已成功且对账未知，应使用同 ID。

**改动与理由。** STAGE3 加强 QUIET 前后保存、停 DMA 与重装边界，INFO、RAM、QUIET 可独立复验。先隔离外设恢复，再测真实长 PUT。

**验证与边界。** 13:46 同 ID 只对账与 complete 成功。13:50 新 ID 完整通过，但该次波形尾部截断，complete 取双端日志和业务回执。

#### 怎样复查这个案例

**取证做法。** 664 笔 MOSI CRC 全对，MISO 前 662 笔通过，尾部两笔错误。第 664 笔离线旋转一字节可恢复响应，区别于案例 04 的两字节。503 上轮累计 117，加本轮通过 662，等于首错 blocks=779。首错 RX 余 511、TX 余 480，已越过完整块边界。清理后寄存器不能反推原 RUN 值。现场曾因诊断中的 MFPR 起始地址和启动打印不同而出现“CLK 被重配”假说，先确认读取同一寄存器再比较。

**为什么先做离线 QUIET。** 它提供可控制的持有、停机和重装时间，让读者在不用真联网的条件下验证外设路径。再用真实 PUT 后立刻发对账请求，覆盖实际边界。源码从 UMA `lc_https_quiet()` 跟到组缓冲回收和重装后 READY，ATS 查业务对账入口。

**复测。** 先看五秒 QUIET 判据，再用 11:26 原 ID 复跑。13:46 确认已有上传，只做业务 complete。用未使用 ID 跑新闭环防止只读到旧 SYNC_SUCCESS。13:50 抓包覆盖 553 个 DATA 块，尾部截断，后段由双端日志验收。后端对象下载需另取证。依据为 1126、1346、1350 报告。

### 11｜QUIET 入口的 CSS 正常回落被全状态比较误报

**现象。** 11:58 INFO 11 笔、RAM 14 笔、QUIET 8 笔，共 33 笔双向 CRC 全对，503 在进入五秒等待之前报 `-231`。STOPCHECK 在 12:07 打到 ENTRY/TRACE_CHANGE。

**目标与定位。** 第一次只知道 `-231`。应在原判断点打印 ENTRY/WAIT/EXIT、触发原因与比较前后的值。函数返回后打一组 FIRST_FAULT 虽有价值，却可能已错过状态变化。

**根因与排查。** 两次 STATUS 为 `0x000F8042 → 0x000F8040`。仅 bit 1 CSS 回落。两次 RX/TX 都 STOP，计数、描述符和 BUSY/RNE/ROR/TUR 未变。

**改动与理由。** CSS 修订仅容纳已经辨认出的回落，仍验证停机、地址、计数、错误位和非法状态。避免把所有快照变化都放行。

**验证与边界。** 13:35 五秒 QUIET 和重装通过，未打印 CSS 回落，不能声称该次再次命中分支。11:26 的首次失步物理原因仍未知。

#### 怎样复查这个案例

| 字段 | 基准采样 | 触发采样 |
|---|---|---|
| SSP STATUS | 0x000F8042 | 0x000F8040 |
| RX/TX CSR | STOP / STOP | STOP / STOP |
| RX/TX 剩余 | 512 / 488 | 512 / 488 |
| 下一描述符 | 同一对地址 | 同一对地址 |

**补课与改法。** 像在 STM32 比较 `SPI_SR` 时先确定各位语义一样，状态等值检查要区分会自然变化的标志和违反约束的标志。UMA/ATS SPI 不共用寄存器位号。本例 SDK 将 bit 1 定义为 CSS。UMA `spi_link_dma_circular.h` 的停止后检查允许已经辨认的入口 CSS 回落，BUSY/RNE/ROR/TUR、描述符、地址和计数仍继续校验。不要整体忽略 STATUS。

**复测。** `app spi2soak 1 1000 5000`。13:35 的 V2 样本 INFO/RAM/QUIET 为 11/14/16 笔，41 笔双向 CRC 全对，五秒持有 1,001 tick、REARM count=1、bad=0，DMA starts 从 1 到 2。第 33 笔末尾到第 34 笔有效帧约 5.0445 s，期间有一个 CS 高时的独立 SCK 边沿，不能计成一笔坏业务。依据为 1158、1207、1335 报告。

### 12｜运行中恢复必须证明坏对被拒绝及下一次可用

**现象。** 14:37 对已完成 ID 执行 witness-once，前两帧 DEVICE_INFO、QUERY 的 witness 从 `0xa35ce719` 改为 `0xa35ce718`，保留有效头及 CRC。

**目标与定位。** 证明检测、重建、确认和下一任务都发生，四项缺一时只记录实际覆盖层级。使用已完成 ID 是为了避免实验重复写入对象。先普通查询建立双槽，再用专用包只做一次注入。

**根因与排查。** 注入模拟槽标记异常，验证故障路径能与业务层区分。单有 PASS 或单边 READY 变动不足以证明双端同步。

**改动与理由。** 检查成对 witness，RX RECOVERY 受控重建，主机验证匹配的 RESYNC ACK。把当前调用结束为 FAIL，避免在结果未知时继续发 HTTP。

**验证与边界。** `1437.atkdl` 捕获全部 8 帧，各 4,096 个时钟，双向 CRC 全对，末两帧 ACK 的 tid/request/cookie 一致。保持供电，`1438.atkdl` 同 ID 34 帧，仅一次 init 后 SYNC_SUCCESS，零 PUT/complete。该注入没有制造真实线路毛刺。

#### 怎样复查这个案例

| 步骤 | 线上观测 | 串口与业务判据 |
|---|---|---|
| 注入前一对 | DEVICE_INFO、QUERY 各 512 B，偏移 504～507 变为 `18 e7 5c a3` | 503 报 PAIR WITNESS 异常，不进入本次 HTTP |
| 恢复 | 后六帧恢复正常 witness，最后两帧为匹配 RESYNC ACK | 两端恢复结果均成功，当前命令仍 FAIL |
| 不重启重跑 | 总计 34 笔，设备查询 8，init 26 | 同 ID SYNC_SUCCESS，265,113 B 已上传及连续进度，无 PUT/complete |

**为什么 witness 异常可以与 CRC 正确同时出现。** CRC 校验头和声明的有效载荷，witness 在尾部协议保留处有独立用途。诊断刻意只碰标记，用来测软件面对坏对的处理；真实位滑移的物理成因仍参考 04 和 04a。读 `spi_link_p4.h` 的 `P4_SPI_WITNESS_TEST` 路径、UMA 成对验收与 ATS `sfile_resync()`。未开启诊断时不能把 witness-once 当普通上传选项。

### 13｜ATS 先就绪，不能让一次无时钟探测锁住下一次

**现象。** 15:02:11 第一次 transfers=0，503 尚未可用。15:02:23 第二次才成功握手，双方 tid 匹配，已完成 ID 只查 init 后 PASS。

**目标与定位。** 最小复现只需要先运行 ATS、后等 UMA 就绪。每次命令从首个日志开始记。第一次 transfers=0 且分析仪在失败窗口内没有 SCK，不能宣称进入了业务或坏帧路径。第二次要看到匹配的 BOOT tid 与业务结果。

**根因与排查。** 未产生 SPI 事务与实际交换后链路失步的后果不同。分析仪在握手前记录了 112 个连续 READY 边沿，间隔 39.3～40.8 ms，为启动信标。

**改动与理由。** BOOTRETRY 在零事务探测失败时可释放探测状态，下一次命令重新观察。发生真实交换或 GPIO 清理失败时保留隔离和握手检查。

**验证与边界。** `1503.atkdl` 及双端日志支持 ATS 先启动、503 后就绪这一条件。握手后 READY 随正常许可变化；较早不规则边沿来源未知。

#### 怎样复查这个案例

**为什么把失败分类。** 还没移出任何一笔时，没有消耗真正的 SPI 槽。可以释放此次探测并让下一次观察。DATA 或握手一旦已上总线，双方槽位和 token 可能已改变。将这种失败与 GPIO 清理失败保留为隔离状态，不能共用“无条件清 fault”的做法。读 `swap_ready_boot_probe()` 和 `sfile_boot_sync()`，画出等待、零笔退出、已发失败和握手成功四条边。

**验收。** 15:03 的波形在握手前最后 4.44 s 有连续启动边沿。最后一笔之后 READY 翻一次并保持约 24.2 s，与正常业务阶段行为一致。复测时两个命令之间保留供电。第二次需同时验证新启动握手、已完成 ID 的 init 和 PASS，才能登记该场景通过。

### 把排障过程写成一条可复现的记录

复盘时按下面顺序填写，空白项标“未采到”，不要用下一轮的截图填补这一轮的缺口。

1. **冻结现场。** 配套固件、SCK、接线、采样设置、从复位起的双端日志和请求身份。判定采集是否跨过实际故障以及最后一次回执。原始业务请求可能含签名，公开记录只保留脱敏字段。
2. **画事件顺序。** 找第一个发生的异常，记录主从各自的阶段、时间、事务数、tid 和请求号。先判断从机是否先 STOP，主机是否真的打过时钟。单端最后一条错误常属于传播结果。
3. **做一个能区分假说的对照。** 例如线端 MOSI 正确而从机槽局部移位，就补同一次 DMA 槽；POST 返回 401，就重建实际请求并用目标 libc 复现。保留替代解释和实验控制条件。
4. **把修复落到可检查的边界。** 能证实的条件才改变。CSS 只接受已查实的允许变化。QUIET 只在安全边界停止和恢复。业务请求结果未知时保留同 ID。原有 CRC、时钟边界和有限期限继续检查。
5. **再验收修复、故障恢复及正常回归。** 修复版另做触发目标分支的测试，与无故障样本分开。用三处判据填记录：本地是否安全结束、下一次是否可执行、服务器或回下载荷是否符合预期。

## 6. 协议、状态和计数

~~~mermaid
sequenceDiagram
    participant A as ATS 上传状态机
    participant U as UMA DMA 与 HTTPS
    participant B as 后端及对象存储
    A->>U: 启动握手及 DEVICE_INFO
    U-->>A: 匹配回包与设备时间
    A->>U: init 请求及 JSON
    U->>B: HTTPS init
    B-->>U: 会话 ID 和 pendingParts
    U-->>A: 响应分页
    loop 每个后端待传范围
        A->>U: 读取源文件范围，分组 DATA
        U->>B: 同一 PUT 内顺序写组
        U-->>A: 恢复 READY，最后回 HTTP 状态
    end
    A->>U: 原文件身份重新 init 对账
    U->>B: 核对连续进度和待传片
    A->>U: 需要时发 complete
    U-->>A: SYNC_SUCCESS 后输出 PASS
~~~

| 量 | 含义 | 现场怎样验 |
|---|---|---|
| 512 B 事务 | 一个 CS 窗口内全双工 | 4,096 个 SCK 上升沿，与 MOSI 和 MISO 一起取样 |
| 双槽 witness | 参与确认槽边界，与语义 CRC 各有检查路径 | 看偏移 504～507，正常小端字节 `19 e7 5c a3` |
| DATA 块与组 | DATA 最多 480 B，组最多 100 个块 | 265,113 B = 552×480 + 153，即 553 DATA 块、6 组 |
| 业务分片 | 后端给出的 offset/length，一片一笔 PUT | partSize 仅为请求提示，检查实际范围和长度 |
| 同 ID 对账 | 复用稳定身份查远端进度 | 已完成时只有 init；已有数据未提交时只 complete |
| SPI 恢复 | 有界停机、重装和匹配 RESYNC | 当前失败退出，下一次明确调用再继续业务 |
