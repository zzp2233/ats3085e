# 代码修改与 Git 提交说明模板

适用仓库：ATS3085E（`D:\ats3085e`，代码树 `TAG_ZS3085E_241230`）与 UMA503-V7（`D:\UMA503\UMA503-V7_OPENCPU_OC_2025.03.14_1644`）。

用途：一次改动在提测/提交前，用本模板产出一份说明。说明是给人看的（接手的人、未来的自己），也是提交正文的来源。**说明先写完，再执行 `git add`**。

参考来源：`UMA503-V7_接入ATS3085E_全程BUG复盘.md`（第五章 5.0 提交注释、附录 A 改动清单）、`UMA503-V7_与ATS3085E_SPI角色互换256字节复盘_20261116.md`（第 13 章 Git 提交前整理）、`UMA503-V7_与ATS3085E_SPI开发全程复盘.md`（第 11 章注释与提交约定）。

## 一、三条硬规则

1. **先定位，再改代码。** 说明里必须有一节讲清"现象 → 拆成哪几个独立故障 → 判据是什么"。没有判据的改动，等于没定位。
2. **每个文件写"改了什么 + 为什么"。** 只写"改了什么"是变更日志，不是说明；只写"为什么"没法复核。行号、旧值、新值尽量写全。
3. **验证结果必须量化，并区分"已证明 / 未证明"。** 写"通了"不算结果，要写 `1000/1000、retries=0、bad=0` 这种可对照的数字。没量的、没查证的，单列一节写清楚，不能混进结论。

## 二、改动说明文档结构（完整版）

文件命名：`<对象>_<动作>_<结果>_<YYYYMMDD>.md`，例如 `SPI_SPEED_V10_RESULT_20261118.md`。放在对应仓库 `docs/`，两仓库需要共享的复盘各存一份相同内容。

```markdown
# <一句话结论：做了什么，到什么程度>

日期：<YYYY-MM-DD>，<时区>。依据：<日志/波形/固件版本>。

## 1. 结论先行
- 通了什么：<可执行的判据，不是形容词>
- 基线版本：3085E <固件名/SHA> + 503 <app.bin 哈希>
- 一句话根因：<最多两个，多了说明没定位完>

## 2. 现象与问题定位
- 现象：<可复现的输入 + 观察到的输出，带具体数值/字节形态>
- 拆解：1) <故障 A 及其责任文件> 2) <故障 B ...>
- 判据：<满足什么条件算通，缺哪一条就必不通>
- 被排除的假设：<假设 → 否定它的实测证据>（这一段最值钱，别省）

## 3. 分文件改动（按依赖顺序，不按修改时间）
| 顺序 | 文件:行 | 动作 | 为什么 | 关联网 |
|---|---|---|---|---|

### 3.1 <文件 A>
```c
- 旧：<原语句>
+ 新：<新语句>
```
- 为什么改：<不这么改会出现什么具体现象>
- 副作用 / 代价：<功能损失、资源占用、行为变化>

## 4. 验证
- 命令：<可直接粘贴的完整命令，含参数含义>
- 结果：<逐项数字，含失败样本>
- 对照：<改前 / 改后 同一指标对比表>

## 5. 边界（未证明 / 存疑 / 不能外推）
- 未证明：<哪条结论只有间接证据>
- 存疑：<现象存在但根因未定位>
- 不能外推：<低速通过 ≠ 高速通过，短帧 ≠ 长帧>

## 6. 遗留与回滚
- 探针：<临时打印/计数器，保留还是清理>
- 回滚：<改哪几行即可退回，是否影响其他功能>
- 下一步：<按优先级列，标注"不建议"的方向>
```

## 四、Git 提交信息模板

### 4.1 标题行

主格式（工程改动，默认用这个）：

```text
修改项：<结果型描述>（根因：<根因一句话>）
```

要点：标题写**结果**不写动作。"打通 UART2 AT 链路并跑通 HTTP GET"是结果；"修改 board.c 引脚配置"不是。

轻量改动可按类型前缀，正文相应缩短：

| 前缀 | 用在什么上 |
|---|---|
| `修改项：` | 功能/链路打通、角色互换、协议升级等有完整七段内容的主提交 |
| `fix(<模块>):` | 单点缺陷修复，一两段说明够 |
| `perf(<模块>):` | 只调性能、日志量、时序，行为不变 |
| `chore:` / `docs:` | `.gitignore`、复盘文档、构建脚本等非功能改动 |

### 4.2 正文（完整版，七段）

段名固定，缺段要写"无"并说明原因。正文手工折行到 72～78 列（终端与 `git log` 阅读友好）。

```text
修改项：<结果>（根因：<根因>）

一、问题定位（先说清为什么动这些文件）
- 现象：<输入 + 观察 + 具体数值/字节形态>
- 拆解为 N 个独立故障：
  1) <故障 A>：<机理，指到文件:行或寄存器位>
  2) <故障 B>：<机理>
- 判据：<同时满足 A 与 B 才通，缺一不可>
- 排除的假设：<假设 → 否定证据>（可选，但误判过的必须写）

二、分文件改动（改了什么、为什么）

1) <文件>:<行>（<这个文件在这条链路里的角色>）
- 为什么：<不改会出现什么现象>
- 改法：<旧值 → 新值，含关键宏/结构体>
- 副作用：<功能损失、资源占用、行为变化>

2) ...

三、验证命令
- <命令原文，含参数范围与前置条件（先开哪个串口、先烧哪端）>

四、验证结果
- <层级 1>：<数字结果>
- <层级 2>：<数字结果>
- 编译：FLASH <n> B、SRAM <n> B（较上版 <±n> B）
- 对照：<改前/改后 同指标对比>

五、未证明与已知限制
- <只有间接证据的结论>
- <根因未定位的现象>
- <本轮未覆盖的场景：高速/长帧/带载/断链恢复>

六、遗留与回滚
- 探针：<tmin/dry、s_dbg_* 等，保留为日志 or 清理>
- 回滚：<改回哪几行即可>
- 下一步：<按优先级；明确写出"不建议"的方向>

七、硬件/环境动作（无则写"无"）
- <拆芯片、改接线、换跳线、改串口工具设置等代码外但缺了不通的动作>
```

### 4.3 正文写作口径

- **一句一条，一条一个事实。** 不写"优化了代码结构""提升稳定性"这类无法复核的话。
- **数字带单位与量纲**：`0.1V`、`812.5 kHz`、`40.715 s`、`58,946 B/s`、`SRAM 927,664 B`。
- **失败形态要写全**：`从机只收到 48~158 字节`、`短帧 231~232`、`全 0x00 / chk=0 相位错位`。失败形态是下次排障最快的判据。
- **"为什么"要指向机理，不是指向操作**：写"PADDRV 默认 4 档只能拉到 1.37V，模组 4.7K 上拉顶住电平，判高=空闲"，不写"把驱动改大就好了"。
- **两仓库联动时，两边正文各自成立，且互相点名**：`配合 3085E 主机…`、`与 UMA503 端保持一致，SHA 43077C3E…4949E1DF`。

## 五、代码注释规范

函数头沿用 STM32 库函数风格：

```c
/**
  * @brief  <作用，一句话，动宾结构>。
  * @param  <参数名> <含义 + 输入约束：范围、单位、是否可空>。
  * @retval <返回值含义；错误码逐个列出>。
  * @note   <硬件独占、超时上限、调用前提、不可重入等>。
  */
```

行尾注释对齐规则（这三份复盘里已经实际执行过，照做即可）：

1. 同一函数内的行尾注释统一对齐到该函数**最长代码行之后**，至少留 4 个空格。
2. `return`、`else` 分支、多行调用的行尾注释也纳入同一列，不要单独缩进到左边。
3. 宏定义组、结构体成员组、同一组引脚（如 GPIO57～60）各自成组对齐，组间不强行拉平。
4. **用空格对齐，不用 Tab。** 换编辑器后 Tab 宽度变化会整片错列。
5. 独立段落注释、函数头保持原位置，不推到代码右边。
6. 对齐只做本轮涉及的函数与声明，**不对整个 SDK 做格式化**。提交前用"整理前后 token 一致"自证无逻辑改动。

## 六、提交前检查清单

两个仓库分别在 git 根目录执行（SDK 源文件原本是 CRLF，`core.autocrlf=false`，必须显式接受行末 CR，否则每行都被报成尾随空白）：

```powershell
git status --short
git -c core.whitespace=cr-at-eol diff --check
git diff --stat
git diff --cached --stat
```

逐项确认：

- [ ] 两份共享协议头逐字节一致（比对 SHA，例如 `43077C3E…4949E1DF`）
- [ ] `artifacts/`、`*.fw`、`*.zip`、`Dump/`、`*.dmp`、临时 txt 日志没有进暂存区
- [ ] `.gitignore` 已覆盖本轮新增的产物类型（转储、备份、日志、缓存）
- [ ] 临时探针（`tmin/dry`、`s_dbg_*`、`brace_check.py` 等）已决定保留为日志还是清理
- [ ] `*.bak_before_*`、`.before_*` 等本地备份未被 `git add`
- [ ] 注释整理没有引入逻辑改动（token 对比 / 重新编译通过）
- [ ] **固件产物哈希与源码对应**：先确认 `artifacts/` 里 `.fw` / `app.bin` 的哈希与本次提交的源码匹配，再提交
- [ ] 说明文档（复盘）已纳入预期提交范围
- [ ] 生成物取消跟踪是有意为之（如 `.lib`、`app.bin`），不是误删厂商唯一可用依赖

## 七、提交拆分与顺序

一次改动默认拆成两个提交，避免"功能 + 杂项"混在一个 diff 里：

1. `修改项：…` —— 源码 + 公共协议头 + 板级配置
2. `chore:` / `docs:` —— `.gitignore`、复盘文档、构建脚本、图标/资源类杂项

顺序：先提交源码（可独立编译通过），再提交文档与忽略规则。

两仓库联动改动：**先提交从属端还是主控端都可以，但两份协议头必须同批提交**，否则中间态是坏的。提交后互相在正文里点名配套版本（`stress-v7 + stress-v6`、`线协议仍为 v6`）。

`push` 与最终 `commit` 由本人执行，工具侧只做 `git add` 前整理与正文起草。
