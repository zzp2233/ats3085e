# ATS3085E 与 UMA503 网络功能迁移校验与实施顺序

**下一步先让 ATS3085E 通过现有 SPI 主从链路取到一条 503 业务命令，并回传可验证的执行结果。**

**首条云端闭环用 `bind_status`，在 ATS 上明确一个本地状态消费者。随后接真实状态和录音控制。上传迁移独立推进，以现有 P4 的服务器对账逻辑为基线。**

目标覆盖当前产品范围内的 MQTT 属性和服务，以及 HTTPS 上传响应。

503 负责云端协议、签名、策略、重试和业务应答。

ATS 负责采集真实状态、操作录音和界面、持有文件并按范围供数。下行业务和上传业务都按这个边界验收。

## 首个开发任务

**交付一条可追踪的 `bind_status` 设置闭环。** 

503 继续校验云端 id、参数和值，ATS 应用绑定状态并回实际结果，503 按当前平台约定回复原 id。

首个本地消费者建议采用 ATS 应用层的绑定状态查询，供诊断直接观察和后续界面接入。

产品 UI 和上传门控分别按明确的产品语义接入。支付绑定状态有独立的使用场景。 [ATS 微信支付绑定入口](/D:/ats3085e/TAG_ZS3085E_241230/application/bt_watch_no_psram/src/launcher/desktop/wxpay_main_scene.c:277)

1. **敲定最小接口。** 
   503 保存期望绑定值和版本，ATS 回报已应用版本与执行结果。
   保留云端 id 在 503，SPI 用独立操作号匹配命令和结果。
   约定空队列、忙、超时、重复、过期版本和两端重启的语义，以及平台响应期限。
   命令号和帧字段在两端同一批定义。
2. **接 ATS 主动取命令。**
    ATS 是 SPI 主机，503 预装 MISO。
   首版在双方空闲、现有 READY/事务条件满足时，由 ATS 用同一 SPI 所有者做有界轮询，读取命令并回传结果。
   利用现有 CRC、序号、会话重同步和 BUSY。轮询间隔依云端响应预算与实测设定。
   普通文件、HTTPS 和 QUIET 期间按既有事务边界仲裁。 [接线与 READY](/D:/ats3085e/docs/ATS3085E与UMA503_P4板端录音上传调试复盘_20261123-25.md:33) · [从机分发](/D:/UMA503/UMA503-V7_OPENCPU_OC_2025.03.14_1644/startup/app_release/demo/spi_link_file_slave.h:924)
3. **等执行结果再应答。** 
   503 保存期望值后异步投递，MQTT 任务继续处理连接和消息。
   成功须匹配本次操作号、版本和 ATS 确认。
   超时按平台约定回复或登记结果未知，后续通过状态核对收敛。
   503 或 ATS 单独重启后，用当前期望版本与实际应用版本重新同步。
   属性查询和上报明确取已应用值或返回状态未知。
4. **跑最小双板验收。** 
   在测试设备发 `0→1→0`，关联同条请求的 MQTT 接收、SPI 送达、ATS 读回和平台应答。
   覆盖非法值、重复 id、ATS 暂不可用、结果丢失、两端各自重启、上传占用 SPI，并复跑原 P4。
   重复消息只应用一次，旧结果不会覆盖新版本，故障阶段在双端日志中可辨识。
