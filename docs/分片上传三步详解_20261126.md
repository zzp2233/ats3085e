# 分片上传三步详解：init / PUT / complete

> 面向 P4 实现。所有字段名以 `lifeiot.cmaiot.cn:8081` 实际响应为准；文中标注「S3 标准」的是通用语义，后端可能改名。
> 参考工程对照：`D:\ZS302A\ZS302A_261010(1)` 的 `file_upload.c`、`cloud.h:234-236`

---

## 0. 一句话

```
init     → 向业务后端申请许可，拿到 uploadId + 每片的预签名 URL
PUT      → 用 URL 把一片字节直接打到对象存储
complete → 把每片的 ETag 交回业务后端，后端校验后合并入库
```

**三步打两个不同的服务器**，这是全篇最重要的一句话。

---

## 1. 两个服务器，两套鉴权

```
                    ┌─────────────────────────────┐
init    ──────────► │ lifeiot.cmaiot.cn:8081      │  业务后端
complete ─────────► │ 管身份、管会话、管数据库      │   HMAC 签名
                    └─────────────────────────────┘
                              │ 签发 URL
                              ▼
                    ┌─────────────────────────────┐
PUT     ──────────► │ life-card.eos-*.cmecloud.cn │  对象存储
                    │ 只管存字节                   │   URL 自带签名
                    └─────────────────────────────┘
```

| | 业务后端 | 对象存储 |
|---|---|---|
| 域名 | `lifeiot.cmaiot.cn` | `*.eos-*.cmecloud.cn` |
| 鉴权 | 请求头 HMAC 签名（设备身份） | URL 里的 `Expires` + `Signature` |
| 证书链 | 视部署而定 | 视部署而定（可能又是一套根证书） |
| 谁签发 | — | 由业务后端签发 |

**推论**：即使 init 通了，PUT 仍可能因为证书链不同而失败。这是两个独立的 TLS 挑战。

## 2. 完整时序

```
3085            503            业务后端              EOS 存储
 │               │                 │                    │
 │ ①算 size+CRC  │                 │                    │
 ├──────────────►│                 │                    │
 │               │ ②POST init      │                    │
 │               │  (imei,size,crc)│                    │
 │               ├────────────────►│                    │
 │               │                 │ 查库：这设备传过哪些片 │
 │               │                 │ 生成 uploadId       │
 │               │                 │ 逐片签 URL          │
 │               │ ③200            │                    │
 │               │ {uploadId,      │                    │
 │               │  pendingParts[]}│                    │
 │               │◄────────────────┤                    │
 │◄──────────────┤                 │                    │
 │               │                 │                    │
 │ ④喂第 N 片数据 │                 │                    │
 ├──────────────►│ ⑤PUT part N     │                    │
 │               ├─────────────────┼───────────────────►│
 │               │                 │                    │ 写入
 │               │ ⑥200 + ETag     │                    │
 │               │◄────────────────┼────────────────────┤
 │◄──────────────┤ ⑦回传 etag      │                    │
 │               │                 │                    │
 │      ... 对 pendingParts 里每一片重复 ⑤⑥⑦ ...        │
 │               │                 │                    │
 │               │ ⑧POST complete  │                    │
 │               │  {uploadId,     │                    │
 │               │   parts:[{n,etag}]}                  │
 │               ├────────────────►│                    │
 │               │                 │ 校验 etag / 顺序     │
 │               │                 │ 合并为一个对象       │
 │               │ ⑨200 {fileId,url}                    │
 │               │◄────────────────┤                    │
 │◄──────────────┤ ⑩业务完成       │                    │
```

**注意 ⑧ 的 `complete` 必须带 ETag**——这是后端确认“收到的那片是不是完整的那片”的唯一凭据。

## 3. 三个接口

### 3.1 init

```
POST /voice-card/device/v1/oss/audio-sync/multipart/init
Authorization: <HMAC 签名>
Content-Type: application/json

{ "imei": "868504079888857", "fileSize": 48001, "crc32": "..." }
```

**响应**（字段名为示意，以实际为准）：

```json
{
  "uploadId": "u-8f3a...",
  "pendingParts": [
    { "partNumber": 1, "size": 48000, "url": "https://life-card.eos-.../p1?Expires=...&Signature=..." },
    { "partNumber": 2, "size": 1,     "url": "https://life-card.eos-.../p2?Expires=...&Signature=..." }
  ]
}
```

**`pendingParts` 的名字就是设计意图**：`pending` = 还欠着的。

后端在 init 时查库，**已经收到的片不会出现在列表里**：

| 场景 | pendingParts 内容 |
|---|---|
| 首次上传 | 全部片 |
| 传了 3 片断线，重新 init | 只剩没传的片 |
| 全部传完但没 complete | **空数组** → 直接去 complete |

**这是断点续传的全部依据**——设备不需要自己记进度。

### 3.2 PUT

```
PUT https://life-card.eos-.../p1?Expires=...&Signature=...
Content-Length: 48000
（无 Authorization 头，签名在 URL 里）

<48000 字节二进制>
```

**响应**：`200 OK`，头里带 `ETag: "abc123"`。

**三个硬约束**：

| 约束 | 违反的后果 |
|---|---|
| 方法必须 PUT | 签名包含方法 → 换 POST 得 403 |
| `Content-Length` = init 报的该片 size | 不一致 → 400 或签名失效 |
| URL 有时效 | 过期 → 403，必须重新 init |

**PUT 是幂等的**：同一 URL 重发同一片，结果仍是“那片是这份内容”。所以网络抖动可以放心重试。

### 3.3 complete

```
POST /voice-card/device/v1/oss/audio-sync/multipart/complete
Authorization: <HMAC 签名>

{
  "uploadId": "u-8f3a...",
  "parts": [
    { "partNumber": 1, "etag": "abc123" },
    { "partNumber": 2, "etag": "def456" }
  ]
}
```

**响应**：`200` + `fileId` / `objectUrl`（业务上这才叫“录音上传成功”）。

**三个约束**：

- `parts` 必须按 `partNumber` **升序**
- 片数必须与 init 时报的 size 能拼出完整文件
- `uploadId` 必须有效

## 4. 四个关键字段

| 字段 | 是什么 | 谁生成 | 失效条件 |
|---|---|---|---|
| **uploadId** | 这次上传会话的编号 | 后端 | 过期 → `404 NoSuchUpload` |
| **pendingParts** | 还欠着的片清单 | 后端 | — |
| **partNumber** | 第几片，从 1 开始 | 后端 | — |
| **ETag** | 每片字节的指纹 | 存储端 | 内容变则变 |

### 4.1 uploadId 要理解到什么程度

```
它是一张"取号小票"：
  init     → 取号
  PUT      → 号已隐含在 URL 里，不用管
  complete → 必须把号抄回去，否则后端不知道你在说哪次上传
```

三个要点：

1. **设备不能自己编**，必须原样保存
2. **有时效**，过期只能重新 init
3. **不要放进日志明文**（它等同一次上传的凭证）

### 4.2 ETag 要理解到什么程度

ETag = 存储端对这一片字节算的摘要。作用只有一个：**complete 时证明“这片是完整的那片”**。

如果某片传输中少了几个字节但没报错，ETag 就对不上 → complete 返回 `400 InvalidPart`。**这是最后一道数据完整性防线**，比 CRC32 更权威（因为它是存储端算的）。

---

## 5. 状态码要分层次看

| 码 | 含义 | 在分片上传里意味着什么 |
|---|---|---|
| **200** | 请求成功 | PUT 的 200 = **这一片收到了**；complete 的 200 = **业务完成** |
| 201 | 已创建 | 有些后端用 201 表示 init/complete 成功 |
| 204 | 成功但无正文 | complete 可能返回这个 |
| 400 | 参数错 | `InvalidPart`（片缺失/etag 不符）、`InvalidPartOrder`（片号乱序） |
| 401 | 未认证 | init 的设备签名不对（你遇到的是 `A0002 设备认证失败`） |
| 403 | 拒绝 | PUT 的签名过期/无效 |
| 404 | 不存在 | `NoSuchUpload`（uploadId 过期）、路径写错 |
| 409 | 冲突 | 同一 uploadId 并发操作 |
| 5xx | 服务端故障 | 可重试 |

**最关键的认知**：

```
PUT 200  ≠  上传完成
PUT 200 只说明"这一片到位了"
只有 complete 200 才是业务完成
```

## 6. 设备侧状态机（P4 直接照这个写）

```
        ┌──────────┐
        │  IDLE    │
        └────┬─────┘
             │ 录音结束，算出 size + CRC32
             ▼
        ┌──────────┐  401/403 ──► 终止（配置问题，重试无用）
        │ INIT     │  超时/网络 ──► 重试 3 次后回 IDLE
        └────┬─────┘
             │ 200
             ▼
     ┌───────────────┐
     │ SAVE_SESSION  │  存 uploadId、pendingParts[]、每片 size
     └───────┬───────┘
             │
             ▼
     ┌───────────────┐
     │ 还有片没传?    │─── 否 ──┐
     └───────┬───────┘         │
             │ 是              │
             ▼                 │
     ┌───────────────┐         │
     │ PUT 下一片     │         │
     └───────┬───────┘         │
             │ 200+ETag        │
             │ 记下 etag       │
             └──── 回到判断 ────┘
                               │
                               ▼
                        ┌──────────┐  400 InvalidPart ──► 重传该片
                        │ COMPLETE │  404 NoSuchUpload ─► 重新 init
                        └────┬─────┘  5xx / 超时 ──────► 重试
                             │ 200
                             ▼
                        ┌──────────┐
                        │  DONE    │
                        └──────────┘
```

**四条重试规则**：

| 失败点 | 能不能重试 | 为什么 |
|---|---|---|
| init 返回 401/403 | **不能** | 设备身份或密钥问题，重试只会一直 401 |
| PUT 返回 403 | 不能重发同一 URL | URL 过期了，要**重新 init** 拿新 URL |
| PUT 网络中断 | **可以** | PUT 幂等，同一 URL 重发安全 |
| complete 返回 400 | 先查 etag，再重传对应片 | 不是简单重试能解决的 |

## 7. 对应到双芯片的通道

| 业务步骤 | 谁决定内容 | 走哪条通道 | SPI 侧序列 |
|---|---|---|---|
| 算 size / CRC32 | 3085 | 本地 | — |
| 发 init | 3085 拼报文 | 503 发 | `START_HTTPS` → `FINISH` → 读响应 |
| 解析 pendingParts | 3085 | 本地 | 响应 >192B 时用 `HTTP_READ` 分页 |
| 每片 PUT | 3085 喂数据 | 503 发 | 一组 `DATA` + `GROUP_END` + `FINISH` |
| 收 ETag | 3085 | SPI 回传 | `ACK` 的 body（192 字节够放 etag） |
| 发 complete | 3085 拼报文 | 503 发 | 又一次 `START_HTTPS` → `FINISH` |

**一个性能提醒**：如果每次 `START_HTTPS` 都新建连接（请求头写了 `Connection: close`），那**每次业务请求都要重做一次 TLS 握手**（DNS + TCP + 握手 ≈ 几百毫秒）。

- 48KB 两片：2 次握手，可接受
- 几十片的大文件：握手开销会变成主要成本

P4 若要优化，方向是“同一会话复用连接”，但这要求 503 的 `spi_https` 支持 keep-alive，属于后续改造项，不在 P4 首版范围。

## 8. 一页总结

```
三步   ：init（拿许可）→ PUT（传字节到存储）→ complete（回执入库）
两个服务器：init/complete 打业务后端，PUT 打对象存储
pendingParts = 还欠着的片，断点续传全靠它
uploadId = 取号小票，PUT 不用管，complete 必须带上
ETag = 每片指纹，complete 时的核对凭据
200 分两层：PUT 200 ≠ 完成，complete 200 才是
四条规则：401 不重试 / 403 重新 init / 网络断可重发 / 400 先查 etag
```
