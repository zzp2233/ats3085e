## 2. 硬件接线与 SPI 基础

### 双板接线

| 信号 | ATS3085E 主机 | UMA503-V7 从机 | 方向、上板检查 |
|---|---|---|---|
| CS | GPIO57 / SPI2_SS | PCM_SYNC，焊盘 31 | ATS → UMA，低有效。按每笔 512 B 数一个独立 CS 区间 |
| SCK | GPIO58 / SPI2_CLK | PCM_CLK，焊盘 30 | ATS → UMA。Mode 3 空闲高，下降沿推出，上升沿采样 |
| MOSI | GPIO60 | PCM_DIN，焊盘 32 | ATS → UMA，送请求、正文与查询。首笔全零时从这条线查起 |
| MISO | GPIO59 | PCM_DOUT，焊盘 33 | UMA → ATS，回传已准备的响应 |
| READY | GPIO61 输入 | I2C_SDA / GPIO50，焊盘 66 | UMA → ATS，1.8 V。双槽协商生效后一次翻转许可两笔 |
| GND | GND | GND | 两板及逻辑分析仪共地 |

焊盘号指模组本体。开发板排针按板卡原理图或通断档核对。GPIO57 要排除振动 PWM 占用，GPIO61 检查输入复用。COM4 为 ATS Shell，实测 2,000,000 / 8N1。COM6 保存 503 启动及应用日志，COM5 115200 为只读 AT 取证入口。

### 第一次看波形时先分清三件事

1. **SPI 是同时收发。** 主机想取得回执也必须提供时钟。某笔 MOSI 的 GROUP_END 仍在输入，当前 MISO 可能是此前准备的回包。因此主机用后续 QUERY 和标识匹配结果。
2. **READY 管接收额度。** 发两笔各 512 B 后，若 503 正在把本组 RAM 交给网络任务，会暂停发下一次许可。此时看到 SCK 无翻转是预期现象。主机报超时才需依据前一次事务类型区分正常网络等待与链路停机。
3. **线速与上传耗时分开。** 4 MHz 下 512 B 的纯线时是 1.024 ms。144,001 B 注入轮实际 339 笔，若只数时钟约 347 ms，而整轮 24.705 s；其余主要是组等待，不能据整轮吞吐反推 SCK。

### 两条网络链路

~~~mermaid
flowchart LR
    PC["PC，申请上传会话和签名地址"] --> B["lifeiot 业务入口<br/>init / complete"]
    PC --> A["ATS，短行装载请求<br/>生成正文并分组"]
    A -->|"SPI DATA / GROUP_END"| S["503，DMA 双槽与组 RAM"]
    S -->|"READY 和匹配回执"| A
    S --> W["独立 HTTPS worker<br/>DNS → TCP → TLS → PUT"]
    W --> O["后端分配的对象存储"]
    M["503 OneNET 任务<br/>LTE → UTC → MQTT"] --> N["OneNET 属性平台"]
~~~

OneNET 的设备登录凭据和业务 HTTP 签名属于不同入口，PUT 又使用后端返回的短期地址。看到 `ONENET PASS` 后仍需独立检查 PUT 和 complete。完整确认关系如下。

| 层次 | 成功条件 | 能定位的问题 |
|---|---|---|
| SPI 双槽 | DMA 边界确认，READY 许可消费正确，双方事务数闭合 | 线端收发、调度、从机是否已停机 |
| 组缓冲 | CRC16 + 位图校验，独立消费者完成后推进组 | 缺块补发、保留旧组、防止覆盖 |
| PUT | 固定 Content-Length，TLS 验证，HTTP 状态和响应由 503 回传 ATS | 接收方拒绝、DNS/TCP/TLS、发送取消与超时 |
| 业务同步 | 原身份再次 init 核对同一会话、连续字节及 pendingParts；complete 返回业务成功 | 对象已写与录音同步完成相差的最后一步 |
| 下载验收 | 用生成规则重建数据并比实际下载文件 | 长度正确但正文损坏、乱序或被覆盖 |

参考 ZS302A + CAT1 的 `cloud.h`、`file_upload.c` 与 `opencpu_protocol.c` 时，借鉴主 MCU / 蜂窝模组职责、`init → pendingParts / PUT → complete`、固定长度和分层确认。参考源码带有 HTTP 降级和 TLS 验证放宽分支，实际启用条件由运行版本决定。UMA 走 SDK 自身网络初始化、socket 与 mbedTLS，保留原 HTTPS 地址、SNI、证书链和日期校验。

## 4. 逐项 BUG 复盘

### 先按症状查找

| 首个异常 | 先读案例 |
|---|---|
| 注册未开始、进 MQTT 就重启、属性没回执 | 02～06 |
| 后端不给 PUT 地址，或发事务前死机 | 07～10 |
| 最先出现 SPI STOP、READY 超时、或首帧全零 | 11～12、15 |
| TLS 校验失败、串口配置不全、PUT 后仍 SYNCING | 13～15 |

### 01｜11 月 19 日，离线 PASS 被误当作 P3 网络完成

**现象与定位。** 用户问参考工程是否先把组数据放 RAM 再上传，并要求先把 SPI 接到业务。16:49 正常轮 48,001 B、127 笔、两组通过。注错与模拟持有轮 2,132 笔、仅补一次、约 22.2 s；到 17:53 审核明确本轮没有 HTTP 行为。

**根因与排查。** 离线消费者能模拟忙和失败，但 PASS 只覆盖 SPI、组 CRC 和缓冲周转。对照参考工程，上传还需要跨入网络 worker 并拿到业务回执。

**改动与理由。** 先在 P1 统一生成源和文件源，让主机按组交付、按位图重发。模拟持有期间不可推进到下一组，保留可重复的离线对照。后续把网络 worker 从 SPI 接收处理摘出，通过有限组缓冲交接，避免在帧热路径直接阻塞做 HTTP。

**验证与边界。** 离线跨组 CRC32 为 `887489ae`，正常与注错一致。高事务数表明当时以频繁查询 BUSY 等待，后续 HTTPS 的 QUIET 才改变查询期间的时钟行为。

### 02｜11 月 20 日，免 SD 启动可见，MQTT 一直没有开始

**现象与定位。** COM6 只有 SPI 描述符自检和平台 PP 输出。DIAG1 加打印后看见注册查询每次返回，120 s 后 IDLE，定位在入网门槛。PC 探针曾收到属性 `code=200`，它提供登录凭据的对照。

**根因与排查。** SDK 原始示例在查注册前做网络初始化、事件注册和 handler 装载，旧代码缺这组调用。NETINIT2 补齐后 `voice=1,data=0` 仍无法继续，而只读 AT 对照出现 `CEREG: 0,1`、`CGATT: 1`、`CGACT: 1,1`。该板固件的通用 dataReg 不适合作唯一门槛。AT 采样发生在部分 COM6 日志之后。

**改动与理由。** 增加启动阶段、返回码、超时和 IDLE；按 SDK 示例初始化。LTE3 改用虚拟 AT 查询 EPS 注册，核对 `n,stat` 中的 stat。保留 UTC 与凭据有效期门槛，APN、CFUN、SIM 选择保持原配置。

**验证与边界。** 真机查询确认有应答。闭源 API 的一次调用仍可能阻塞，应用层的循环期限只能约束可返回路径。免 SD 私有构建使用本地配置，发布源码使用独立配置入口。

### 03｜LTE3 把已注册的 CEREG 回包判成未注册

**现象与定位。** 内部虚拟 AT 持续打印 `rc=0 stat=-1 bytes=11` 和 `+CEREG: 0,1`；查解析器发现外部 COM5 和内部 SDK API 的响应契约不同。

**根因与排查。** 旧解析要求正文包含最终 OK，实际 SDK 用 rc 给出完成状态，正文只包含 CEREG 行。

**改动与理由。** LTE4 仅在 rc 为 0 后解析，允许正文末尾没有 OK，保留 ERROR、重复状态、单字段 URC、截断与越界拒绝。这样既接受实机格式，也不会把 API 失败时的残留缓冲当成成功。

**验证与边界。** 历史 13 项 ARM 模型覆盖 11 字节样本及本地/漫游/未注册。后续真机进入 UTC 和 MQTT 初始化，证实该收窄后的判断可推进。

### 04｜MQTT_INIT 后接收任务 DataAbort

**现象与定位。** LTE 和 UTC 已就绪，COM6 反复在 `ummqtt_recv_ta` DataAbort 后 Silent Reset。

**根因与排查。** 实际 SDK 库内 `um_mqtt.o` 的反汇编显示初始化先创建优先级 80 的接收任务，再写入客户端指针，接收入口没有空指针保护。调用任务原优先级 90，接收任务可能抢先读空指针。

**改动与理由。** `mqtt_init_guarded` 在 SDK 初始化附近临时把调用任务优先级提至 79，返回后恢复。调用前落 guard 标记，完成且恢复后删除。若遇初始化中断重启，保留现场并停驻，避免陷入重启循环。保持网络连接阶段原调度。

**验证与边界。** 后续上板越过 INIT，到达 CONNECT/SUBSCRIBE/PUBLISH。反汇编支持已观察到的竞态路径，保护范围为当前初始化顺序。检查 guard 时保留文件系统内其他数据。

### 05｜已在线却没有属性回执，随后控制台显示离线

**现象与定位。** 15:17 连接、订阅、发布 rc 都为 0，随后属性回执超时，任务按逻辑停驻。对照 PC 同一属性/Topic、先后两种编号。

**根因与排查。** 旧请求 ID 带连字符且超过 13 位。PC 的纯数字编号回 `code=200`，旧格式回 2405；原固件解析只接受三位以内 code，将四位错误静默丢弃。2405 是 PC 对照证据。

**改动与理由。** MQTT6 生成 13 位数字关联编号，接收非负 int 错误码并校验类型与范围，只将匹配 ID 的 200 判为成功。追加过滤及结束原因日志，保留凭据脱敏。

**验证与边界。** 板端后续成功上报属性。坏格式是否返回相同错误以采集实际回执为准，登录在线和发布 API 返回 0 的证据只到相应阶段。

### 06｜属性下发 1022 和全选读取 10414

**现象与定位。** MQTT 上行已通，控制台对 `bind_status` 下发失败，后续全选 battery、bind_status、charge_state 又报 10414。

**根因与排查。** 应用原先只有主动上报探针，缺对应订阅和处理。MQTT7 的 get 仅接受单项 `bind_status`，全选超出实现范围；10414 截图缺同一时刻 COM6 回执，不能锁定具体响应分支。

**改动与理由。** 实现 `onenet_downlink.c` 的 property/set 与 get，校验属性和请求 ID，写本地镜像后回包，保持本版本支持范围可检验。

**验证与边界。** 16:07 订阅 set/get 成功，下发 0 的匹配回执 200、保存与本次读回通过。多属性、重新启动后加载和 0→1→0 替换还需分别复测。11 月 23 日 OneNET 短期配置续期只改变本地配置和私有包，业务签名另行核验。

### 07｜业务 init 401 / A0002，没有可用 PUT 地址

**现象与定位。** 11 月 20 日 PC 可以验证业务入口 TLS，但 init 收到 401 / A0002。对照附件里的设备接入记录、串口与 PC 工具输出，OneNET 已在线不改变这次业务 HTTP 的返回。

**根因与排查。** 错误定位于业务会话认证，发生在分配对象存储前。复算参考工程的签名路径并对照服务器时间。后台登记的精确变化原因无服务端记录。

**改动与理由。** 用 `lifeiot_direct.py` 按参考 API 对同一身份申请并保存本地会话，保留相同内容和文件标识来查询 init。DigiCert Global Root G2 追加到公共信任链以覆盖业务入口验证。签名只用于对应业务路径，私有信息落 `.local/`。

**验证与边界。** 11 月 23 日 10:34 init HTTP 200、`PENDING_FIRST_PART`，取得 48,001 B PUT 地址。这时正文尚未发，首次 401 的后台原因未知。

### 08｜11 月 23 日，503 无会话清理触发 free(NULL)

**现象与定位。** COM6 重复报 `free address is NULL`、`osa_mem.c:1305`，任务 `spi_link`，随后 Silent Reset。COM4 的启动横幅也可能来自现场刷机。

**根因与排查。** SDK 的释放函数遇 NULL 断言，既有模型允许释放空指针并替代了真实 HTTPS 清理。故障可发生在尚未分配元数据或响应缓冲时。

**改动与理由。** 在 `sl_file_discard()` 和 `spi_https_reset_response()` 判非空后释放，保持多次清理安全。模型按 SDK 语义执行，增加真实 HTTPS C 的 ARM 测试。

**验证与边界。** 历史 38 项 SPI、4 项 HTTPS ARM 模型通过。10:58 COM6 未再见原断言，后续入网超时期间用户确认缺 SIM；按硬件条件恢复后再进入网络验收。

### 09｜ATS 上传前 HCI 随机源崩溃

**现象与定位。** `opcode 0x2018 err:-11`，shell_uart Usage Fault、PC=0。旧 ELF 追到 `sfile_run → bt_rand → prng_reseed → HCI`，还没有 SPI 请求。

**根因与排查。** 蓝牙 LE Rand 超时后的 SDK 分支调用回调，PC=0 与空回调一致。把熵源和上传启动解耦，可避免蓝牙链路状态影响请求。

**改动与理由。** `spi_link_entropy.h` 走 Leopard 安全引擎 TRNG，取 48 B，设置有限等待、占用检查和明显异常样本检测。请求缓冲改为堆分配，退出清零释放。随机数获取失败在打开 SPI 前终止。

**验证与边界。** 历史 33 项 ARM 模型通过，11:38 真机报告 `SE_TRNG bytes=48 ret=0`；随后首个 START 后 READY 超时，属于新阶段。模型不认证随机源质量。

### 10｜降到 1 MHz 后 transfers=0

**现象与定位。** 11:53 有 48,000 B 到达，从机报网络连接阶段 -3 与 SSP ROR。接着试图降频隔离，13:40 读到最低请求频率 2,285,715 Hz、`ret=-34 transfers=0`。

**根因与排查。** 测试配置没核对 32 MHz HOSC 分频，/14 后约 2.286 MHz，1 MHz 无法达到。之前模拟 SPI open 的模型掩盖了限制。

**改动与理由。** `SFILE_HTTPS_HZ` 改为 4 MHz（/8），测试直接执行生产时钟选择分支并验证拒绝不可达时钟时不写寄存器。

**验证与边界。** 历史 34 项模型通过，后续真机读回 4,000,000 Hz。11:53 的 -3 仍缺 DNS/TCP 细分记录，4 MHz 只让新请求能发出去。

### 11｜首组收齐后 -216，网络取消日志反而先出现

**现象与定位。** 13:56 主机 117 笔、从机完成 115 笔，首组正文已达 503，最终主机 READY 超时 -116。14:13 记录 DNS begin → SPI RECEIVE -216 → DNS ready 后 cancel。

**根因与排查。** SPI 先失败，错误清理取消 worker；旧代码等清理完成才输出 STOP，且取消信号被消费后再次查询显示未取消。清理前快照 `rx_rem=182 tx_rem=232 ror=0 tur=0 pair=1` 说明收到部分帧，具体硬件触发仍未定位。

**改动与理由。** DMA/SSP 的 FIRST_FAULT 在清理前取样；取消请求一经观察在当次请求内保持，下一请求重置。DNS、TCP、TLS 与 cancel/timeout 分开打印，连接成功后再检查取消。

**验证与边界。** ARM 模型覆盖清理改变长度和一次性取消复读。14:13 实机已确定因果顺序。该轮未进入 TLS，无法用它评价证书或服务器。

### 12｜焊线后首帧全零，与首组后超时分别处理

**现象与定位。** 14:35 首笔 512 B 全 00，`VALIDATE_RECYCLE -217 blocks=0 bad=1`。14:42 再焊接后首帧全零未出现，首组后仍在 DNS 期间 -216。

**根因与排查。** 两次失败阶段不同。全零应从 MOSI、共地和 pinmux 检查，单看值不能定位焊点。第二次保留首错 `rx_rem=246 tx_rem=472`，说明重焊后仍有部分帧故障。

**改动与理由。** 用两端重启后的 RAM 试验隔离网络，再在完整双槽边界引入 QUIET。503 在 GROUP_END/FINISH 实际网络工作时保留组缓冲，等待期间不发布新 READY，每个 tick 让出 CPU 并复查边界；worker 返回后才归还许可。避免在已观察到失败的网络工作窗口继续打 QUERY。

**验证与边界。** ATS 对已开始的组/结束命令使用剩余总期限，组 35 s、FINISH 120 s；普通 READY 仍 2 s。503 组等待 30 s、FINISH 115 s。两端成套复测后 14:49 已能回传 TLS 错误，底层部分帧机理仍待波形。硬件故障发生在命令前的 16:23 首次注入也属于单独观察，见第 15 项。

### 13｜DNS、TCP 已通过，TLS -9984 / verify 0x08

**现象与定位。** QUIET 的 14:49 轮在约 1.834 s 后收到失败状态，SPI 无同类超时，DNS、TCP 成功，TLS 返回 NOT_TRUSTED。

**根因与排查。** 动态对象存储地址的证书链经 SHECA OV Server CA G5 到 UCA Global G2 Root。它与业务入口的 DigiCert 链不同，原 503 信任根缺这一项。

**改动与理由。** 新增公开 UCA 根 DER；保留已有 ISRG 与 DigiCert 根、TLS 1.2、主机名与有效期校验。PC 用仅该根及板端套件核对握手，编译后检查包内三根均存在。

**验证与边界。** PC 握手只证明对应信任链。在 15:20 之后，普通 PUT 和注入实机返回 200 才证明 503 本轮通过。

### 14｜自动串口装载乱码，PUT 并未开始

**现象与定位。** 15:01/15:03 两轮 clear 无 ACK，元数据为 0，串口乱码。前面的长命令也不适合人工粘贴到板端行缓冲。

**根因与排查。** COM4 实际 2 Mbaud / 8N1，原脚本默认 115200。元数据未完整装载与 HTTPS 失败的表现应按阶段区别。

**改动与理由。** `p3_serial_send.py` 要求显式 baud，校验 begin、总长度、连续偏移、CRC、短行和命令。每条等匹配回执，允许只校验或只装载，正式 PUT 发一次，错误不盲重试。用于保存结果的证据目录仍是私有的。

**验证与边界。** 15:20 重新实测 48,001 B，127 笔、两组、HTTP 200、零补发。工具与板端回传已闭合；下载及 complete 证据在下一项。

### 15｜PUT 成功后业务仍未显示，如何验证完整交付

**现象与定位。** 15:20 PUT 返回 200 后，同一会话重新 init 显示字节已齐且无 pendingParts，但状态还在 SYNCING。16:23 注入首次尝试在发送前失败：COM6 16:22:57 已停机，`blocks=0 rx_rem=511 tx_rem=480 eor=1 busy=1`；主机仅发一笔即超时。

**根因与排查。** PUT 只把内容交给对象存储，业务入账还要 complete。首次注入失败发生在 worker 启动前，工具拒绝继续 complete；上电半帧成因未确认。

**改动与理由。** `lifeiot_direct.py upload` 执行 init、串口上传、结果核验、同身份 init 预检、complete。检查两个会话 ID、长度、连续字节、pendingParts、HTTP 和业务码。板端测试包在正文 TLS 发送回调对每组注入约 3 s WANT_WRITE，复用生产重试、取消、总期限与 QUIET 缓冲所有权；默认关闭注入开关。

**验证与边界。** 两板完整断电恢复后，16:35 四组为 48,000/48,000/48,000/1 B，不可写次数 495/498/497/598，四组 `guard_ok=1`。主从均 339 笔，主机总耗时 24,705 ms，group_wait 24,151 ms，CRC32 `23122b0b`。PUT 200 后电脑确认同会话 `SYNC_SUCCESS`，下载 144,001 B 与生成图案逐字节一致。板端注入和真实服务器慢收分别记验收。PC complete 仍由电脑执行。普通 48,001 B 的下载也独立核对通过。用户提供的复核记录还写明，小程序在电脑侧 complete 后显示“已同步”。该页面状态属于业务侧证据。

## 6. 512 字节协议、分组与统计判据

### 一笔线上事务怎么看

| 区域 | 内容 | 用于定位 |
|---|---|---|
| 0～3 | 方向、版本、命令、保留 | 先用命令字段辨认控制还是 DATA |
| 4～7、8～11 | 传输 ID、块索引或组首索引 | 区分不同 HTTP 请求与上一次会话 |
| 12～15 | 请求编号和有效长度 | QUERY 只有匹配控制请求才能采用 ACK |
| 16 起和 510～511 | 最多 480 B 有效载荷，尾部 CRC16 校验头和有效载荷 | 短尾长度从头取，512 B CS 长度仍固定 |

扩展通道用 `START_HTTP`、`HTTP_META` 配置请求，元数据上限 3,072 B。其后使用 DATA、GROUP_END、QUERY、FINISH、HTTP_READ。经典短地址 HTTPS 与扩展 HTTP 路径共存；响应字段长度应按实际命令看，扩展路径每次读取正文最多 400 B。短行 Shell 装载与 SPI 上的 HTTP_META 发生在两个不同接口。

### 用一个 1 B 尾组练习算数

48,001 B 是 100 个满块加 1 个短块，组成 48,000 B 与 1 B 两组。实测主机 127 笔，包含探针元数据、控制、查询及填充，因此主机发送笔数会大于 101。两端应对账实际事务而非 DATA 块数。组 CRC 与最终 CRC32 用于核对传输，HTTP 200 对象写入与业务 complete 各有独立状态。其他 AI 的 P4 分析指出一个 4 MiB 业务分片会拆成88 个 SPI 组，但仍共享一笔 PUT 的 Content-Length 与最终 HTTP 状态。

## 7. DMA 首错、网络阶段和错误码

| 最先观察到 | 对应层次 | 此时查什么 |
|---|---|---|
| transfers=0，-34 | ATS 打开 SPI 时钟配置 | 源、分频、最低请求值。本轮 32 MHz HOSC 的 /14 约 2.286 MHz |
| RECEIVE -210，ror=1 | 503 SSP 接收溢出 | RX DMA 请求、FIFO 状态、同一 CS 内 SCK |
| RECEIVE -216 | 503 未在等待内确认完整事务/双槽 | FIRST_FAULT 的 rx_rem、tx_rem、EOR、BUSY、描述符位置。区分是上电后还是本组工作中 |
| VALIDATE_RECYCLE -217 | 503 接收数据或边界验收 | FIRST_BAD，逐字节核查 MOSI、CS 与接线 |
| 主机 READY -116 | 主机未在期限内获得新许可 | 先找 COM6 是否已 STOP，再查操作是 DATA、GROUP_END 或 FINISH |
| SEND at=0 error=-3 | 网络连接路径 | 新版按 DNS/socket/TCP 日志拆开。结合 FIRST_FAULT 与 cancel 判断先后 |
| TLS -9984 / verify 0x08 | TLS 证书验证 | 核对实际对象主机的信任链、SNI、时间 |
| HTTP 401 / A0002 | 业务 init 认证 | 核对对应 API、设备登记和签名输入 |
| HTTP 2xx、业务仍 SYNCING | 对象上传完成，业务确认待推进 | 复查同一会话的连续覆盖、pendingParts 和 complete |

DMA 两端的运行、计数和中断可能跨时刻变化。保存清理前与清理后快照，先看哪个事件先发生。网络 worker 的 error/cancel 输出顺序也会受清理时任务切换影响。

## 9. 如何复现验证、采集波形

1. 按 SPI 复盘的构建/烧录章节准备两端，ATS 使用 FW，503 使用 Aboot ZIP。私有包可能包含短期设备配置，配置失效时按本地配置和当前构建入口重新生成。禁止把带凭据的包、原始签名 URL、私有元数据或设备标识写入 Git。
2. 从开机同时保存 COM4/COM6，核对描述符自检、READY 与任务状态。若命令前已 STOP，保存第一份快照，先观察两端断电重启与时钟，再复测无网 RAM。 `app spi2rampair 101 --hz 4000000` 可用于隔离 SPI，切回上传前重新同步两板。
3. 真实后端选择有权限的测试设备与新文件身份。下列示例从仓库运行，`DeviceId` 为本地设备号，`BusinessKeyFile` 为本地业务签名文件。关闭串口助手的 COM4，让脚本独占，COM6 继续记录。正常包先测 48,001 B，注入包测 144,001 B 使用独立会话目录。

~~~powershell
python tools/lifeiot_direct.py upload --imei $DeviceId --bytes 48001 --directory .local/p3-normal-check --secret-file $BusinessKeyFile --port COM4 --baud 2000000
~~~

4. 分阶段时可用 `init` / `refresh` 生成本地命令；`p3_serial_send.py --check --commands <命令文件>` 校验而不占端口。用 `--stage-only --baud 2000000` 可以只装载。串口回执缺失先停，按已确认的会话状态恢复。先查询，再判断是否还需 PUT 或 complete。
5. 对比固定长度、COM4 transfers 与 COM6 本轮 blocks 增量、各组 CRC 与服务器进度。需要隔离服务器失败时，可用有证书的可控接收器测慢读、非 2xx 回传和恢复；真实后端条件单独记录。普通包和注入包的测试证据各自保存。

### 用一份波形区分线端、DMA 与应用

从复位前开始保存双端串口，分析仪最少接 CS、SCK、MOSI、MISO、READY 并共地。首帧异常以 CS 下降沿触发，数该低电平内 4,096 个 SCK 上升沿，导出原始采样和解码结果。标记 START、第一组结束或出错前最后一笔，并对齐 COM6 FIRST_FAULT；可选记录 503 GPIO53（MAIN_RTS 焊盘 23）作为探针，须确认固件启用了相应复用。网络等待测试还要采两次 READY 的间隔，对照同组 worker 返回、首错/取消及下一笔 QUERY。TIMEOUT 后先保存该轮日志。

验收时把普通 48,001 B 与注入 144,001 B 分行登记，记录当前是否专用注入包、主机事务、从机增量、每组开销、HTTP 状态、业务回执和下载全文摘要。若执行真实慢收，再记录限制来源和实际服务器或网络的行为。

<a id="fifo"></a>

## 14. 从 TXE/RXNE 到 FIFO、DMA 和组缓冲

F103 教程中写 DR 后等 RXNE 再读 DR，下一次函数调用从下一字节开始。TXE 说明可写下一项，等整笔结束还涉及移位寄存器、RX 与外设状态。当前硬件把这个动作放大到 512 B。有限 TX DMA 负责喂 FIFO，RX DMA 负责把已经取到的值放入内存，503 则由两个描述符分别服务每个方向。

| 缓冲 | 容量或尺度 | 何时释放 |
|---|---|---|
| SPI FIFO | 外设样本队列 | TX 连续补，RX 随硬件请求排空 |
| RX DMA 半区或槽 | 512 B，一对合计 1,024 B | 对应 DMA 事件及外设空闲检查完成后，由 CPU 处理并回收 |
| 503 组 RAM | 最多 48,000 B | 网络消费者确认本组结果后才能覆盖 |
| 业务分片 | 后端的 offset 和 length | 通过后端查询核对上传已覆盖，再调整业务进度 |

练习在 14:13 和 16:35 两轮日志上区分硬件部分帧与正常等待。前者有 RECEIVE -216 及半帧剩余计数，后者长时间等待但最后 HTTP 200、双端事务闭合。

## 15. 把 STM32 初始化翻译成两套 SDK

在 11-2 的 `MySPI_Init()` 圈出 RCC、GPIO 复用、CPOL/CPHA、软件片选四块。ATS 把这些分布到板级配置、Zephyr 设备绑定、驱动和传输配置。UMA 在应用任务内通过 `um_spi_init()` 初始化 SSP2，再核对从机方向、DMA 映射和描述符。RTOS 应用不一定在 main 里直接调用收发，ATS 用 Shell 启动此次传输，UMA 则从应用启动任务进入。

| STM32 观察点 | ATS | UMA |
|---|---|---|
| GPIO AF 与 RCC | 板级 pinmux、`soc_clock.c` 回读 | SSP2 复用与状态回读 |
| 主机 CPOL/CPHA、分频 | SPI2 Mode 3 / 4 MHz | 同模式，使用外部 SCK |
| 外设 IRQ / DMA | READY 唤醒与 RX 半区事件 | 独立任务等待描述符和 worker |
| 下载后串口打版本 | FW 启动横幅 | Aboot ZIP 的 app 启动标记 |

<a id="ats-init"></a>

## 16. 第一步：在 ATS 检查板级资源和请求入口

先在 `system_app_shell.c` 找命令注册，再检查 `spi_link_put_probe.h` 是否成功装载完整元数据，及 TRNG 是否已返回成功。之后才会进入 `sfile_run()` 打开 SPI。类似 STM32 调完 `SPI_Init()` 还要检查时钟是否到目标引脚，本项目既要确认 SPI2 的 HOSC 分频回读，也要看 GPIO61 token。出现 `transfers=0` 从这条调用链往回找。若已发 START 且后一笔超时，再去 COM6 查接收及任务状态。

<a id="swap"></a>

## 17. 第二步：从 SwapByte 到 SPI 打包与分组

用 PA4 片选包住多次 `rx[i] = MySPI_SwapByte(tx[i])`，可以先想象每笔交换 512 次，芯片各拿回 512 B。项目中 DMA 把循环搬走，报文内容仍需软件构造。用 48,001 B 举例，前 48,000 B 经 100 笔 DATA 运入第一组，组确认及查询结束才交付最后 1 B。每笔 DATA 都有序号与 CRC，让主机在已知缺项时只补对应块。

如果将来服务端要求 4 MiB 的一个 part，按 SPI 组要传88 组，网络任务仍在同一请求中累计发送并只返回一份最终 HTTP 状态。画图时可给 CS、SPI 组和业务 part 分别画边框。

<a id="host"></a>

## 18. 第三步：沿调用链读 ATS 主机

`sfile_send_body()` 从源数据读块并组帧，`sfile_control()` 处理 GROUP_END 和 FINISH；`sfile_exchange()` 等待许可并开一笔传输。把这三层对照 STM32 的应用操作、W25Q64 指令、SwapByte，逐层记入参、完成条件和异常返回。底层从 ATS DMA 要同时读剩余计数及 SPI 状态，协议层则确认传输 ID、请求号和控制命令一致。

普通 READY 等待 2 s。HTTPS 组 / FINISH 的较长期限只在相应控制操作展开后应用，每次取剩余预算。练习用 14:13 的 `-116` 和 16:35 的长等待对照，前者应沿 COM6 找首错，后者应查 QUIET、worker 耗时和成功回执。

<a id="slave"></a>

## 19. 第四步：沿 UMA503 从机读缓冲交接

STM32 从机把应答预装后，需要等主机拉 CS。这里先由 503 两个描述符环预取与接收，再由 `lc_pair_finish()` 校验边界。DMA 确认和 cache 交接后，`sl_file_receive()` 处理正文或控制。GROUP_END 满足时把组交给消费者，QUIET 期间不再发 READY，既不让主机继续打 QUERY，也不覆盖 worker 使用中的组。待网络返回，再检查 DMA 状态、恢复许可并返回相应的控制结果。

| 读代码时的观察点 | 可以怎样验证 |
|---|---|
| 当前槽还是下一槽 | 用描述符指针和剩余量解释边界，结合 cache 操作 |
| worker 是否持有组 RAM | 对照 GROUP_END、QUIET 标记、guard_ok、下一 READY |
| 错误导致清理 | 验证 FIRST_FAULT 出现在清理快照之前，取消在本请求内保持 |
| 结束后处理 HTTP | 依据状态、响应长度与分页读取判断完整性 |

<a id="w25"></a>

## 20. 第五步：从 Flash 指令走到 HTTP 文件同步

Flash 读取有指令、地址和长度。P4 也用服务器指定的 offset/length 读源文件，再把字节经 SPI 交给 503。差别在于 HTTP PUT 使用短期 URL、跨多个 SPI 组，并需复查后端覆盖。可以用下面的对照区分「可以读出数据」「数据已到对象存储」「记录已经同步」。

| 操作 | 当前证据 | P4 应怎样推广 |
|---|---|---|
| 从某地址回读一段 | 这次主机生成可复算的固定数据 | 使用封口录音文件和有界范围读取接口 |
| 请求后确认设备状态 | 503 把对象存储 HTTP 200 回传给 ATS | 分离可恢复错误与结果不确定，必要时重新 init |
| 应用确认 | 电脑查同一会话、连续字节、pendingParts 并 complete | 板端接入后按结构化返回驱动状态，下载独立验收 |

<a id="tasks"></a>

## 21. 补课：任务、锁、期限与可见性

裸机的 `while` 等 RXNE 通常只有一个执行流。这里 ATS Shell、503 SPI 接收、HTTPS worker 与 OneNET 任务都可能被调度。SDK 初始化的优先级改变应只覆盖易出竞态的小窗口。数据通路用 cache clean/invalidate 和屏障交接，同步对象控制谁执行，二者各解决一类问题。

长任务应区分三个时钟：SPI/DMA 的接收等待、一次组操作的剩余期限、DNS/TCP/TLS 自身的超时。QUIET 不收新的 SPI 命令，取消的立即性受当前边界和同步 DNS 影响，优先保留「停止推进、到安全边界后清理」的语义。上板明确记录哪层先超时，避免给所有期限统一加秒数。

## 22. 其余改动与 P4 的实际缺口

### 从录音回调到可按偏移读取的文件

新 AI 复核追到 `src/user_comm/ap_record/record_app_media.c` 的 OPUS、16 kHz 配置及 `record_app_uploadstream.c` 的回调流。现有流没有可用 seek/回读，不能直接作为断点上传的数据源。先用封口、可播放文件验证板端单片，随后再把录音输出送进有界队列和存储线程，停录后同步关闭文件才进入待传队列。原始 OPUS 帧的组织形式和可播放容器需核实。时长、扩展名、MIME 与实际编码保持一致。

文件在会话期间应保持稳定，持久化 localFileId、recordedAt、路径、长度、摘要及状态。参考契约的 fileMd5 是头最多 100 B、尾最多 100 B（与头不重叠）及长度 4 B 小端的采样摘要。全文验收仍用完整摘要和下载比对。掉电恢复需以目标文件系统实测为准，不能凭 rename 推定覆盖原子性。

### 把可复用的 P3 能力与待实现的 P4 接口对上

| 场景 | 计划中的边界 |
|---|---|
| 板端 init 与 complete | 复用参考路径的业务签名契约，先序列化固定 JSON 字节，再算摘要与签名；一次请求一个 tid |
| 收到 pendingParts | 完整校验 HTTP、业务状态、会话和列表。验证 offset/length/partNumber，缺失或截断不能视为空 |
| 正常 PUT | URL 和编码原样使用，按后端要求的请求头发送；业务签名头只用于业务入口 |
| 过期 403、PUT 或 complete 响应丢失 | 有界重查 init，依据待传范围推进。区分 uploadedBytes 与连续进度，不用总字节数猜偏移 |
| 响应容量 | 503 扩展路径上限 16 KiB，HTTP_READ 分页只减少单笔 SPI 载荷。板端流式 JSON 解析也不会扩充 503 整份响应缓存 |
| 安全确认 | 同一会话两个 ID、待片为空、长度匹配后执行 complete，确认 SYNC_SUCCESS 才推进本地状态 |

`tools/lifeiot_direct.py` 的 complete 预检查和 `tests/recording_multipart_p4.py` 的 403、响应丢失、多片模型可用作参考。复刻资料包的《设备分片上传与断点续传对接文档》《设备云存对接文档-PUT直传》提供后端契约，`1.md`、`zk.md` 提供打包与歧义排查线索。以上规则是待实施和验收的设计，现场 P3 仍由电脑端驱动。

## 24. 两端执行流程、函数调用与 STM32 对照

~~~mermaid
sequenceDiagram
    participant P as PC 工具
    participant A as ATS 主机
    participant U as UMA SPI 从机
    participant W as UMA HTTPS worker
    participant B as 业务入口与对象存储
    P->>B: init 获取本次 PUT 地址
    P->>A: 串口装载元数据，spi2putgen
    A->>A: 取 TRNG，sfile_run
    U-->>A: READY 初始许可
    A->>U: 会话协商与 HTTP_META
    loop 分组发送
        A->>U: sfile_send_body，DATA / GROUP_END
        U->>W: 完整组交给 worker
        Note over A,U: lc_https_quiet 期间不归还 READY
        W->>B: TLS PUT，持续写同一个请求
        W-->>U: 本组消费结果
        U-->>A: 复查边界后翻转 READY
        A->>U: QUERY
        U-->>A: 后续事务返回匹配的组回执
    end
    A->>U: FINISH 与扩展响应读取
    U-->>A: HTTP 状态及响应
    A-->>P: 双端对账数据与上传结果
    P->>B: 同一会话再次 init 检查，然后 complete
~~~

把图的 A→U 对照 STM32 的 `MySPI_Start() → SwapByte() → MySPI_Stop()`，先圈出每次 CS，再往上圈一次 READY 的双槽和一组数据。右侧 HTTPS worker 及电脑会话负责更高层的确认。OneNET 的入网、UTC、MQTT、属性回执走独立任务，可对照第 5 章第 6 项。
