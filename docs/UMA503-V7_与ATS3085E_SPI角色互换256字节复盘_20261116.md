### 3.2 关于丝印名的提醒



* 表中 DIN/DOUT 是模组在 **PCM 复用功能**下的命名（表 13：DIN=32 为 DI 模组输入，DOUT=33 为 DO 模组输出）。当前 503 作从机：模组 DOUT(33) 就是从机数据线输出，接 3085 GPIO59（MISO）；模组 DIN(32) 是从机数据线输入，接 GPIO60（MOSI）。两根数据线不要互换。切到 SSP2 复用后引脚方向由内部 pinmux 决定，最终以实测连通为准。

* 脚号来自《UMA503-V 硬件开发手册 V1.2》表 13（PCM/I2C 接口引脚定义）。开发板排针上的编号和模组焊盘号不是一回事，以模组脚号 / 规格书为准，必要时用万用表通断档核对。

* GPIO57 原来被电机 PWM 占用，本次已在板级配置里释放并关闭振动设备；GPIO59、GPIO60 均复用 `MFP_SPI2`。

## 4. 给只学过 STM32 的人补新概念

本章把今天反复出现、但 STM32 入门例程里没讲透的概念，用你熟悉的 W25Q64 读写例程做类比。

### 4.1 主机和从机，到底谁在产生时钟

STM32 例程里 MCU 永远是主机，`SPI_Init` 后由自己的 SCLK 引脚给 Flash 发时钟。这次反过来：



* **主机（3085E）**：拉低 CS，自己产生 SCLK，每个时钟沿同时发一位 MOSI、收一位 MISO。

* **从机（503）**：自己不产时钟，SCLK/CS 都是输入；线上来一个时钟才移一位。从机必须在主机时钟到来**之前**把要回的字节放进 TX FIFO，错过的首字节不能事后补写追回。

类比：主机是提问的人，按节拍一句一句问；从机必须把答案备在桌上，轮到它说的时候直接念，不能现想。

### 4.2 全双工：一个时钟，两边各移一位

SPI 是全双工：每来一个有效采样时钟，主机移出一位到 MOSI，同时从机移出一位到 MISO，两条方向互不等待。STM32 读 Flash 时 "发一条读指令、再读回数据"，本质上也是在同一组时钟里两边都在移位，只是主机发的指令字节期间收到的内容是无关的。

本次链路一帧 256 字节，就是同一组 2048 个时钟里，主机把 256 字节请求移给从机，从机把 256 字节应答移回主机。

### 4.3 FIFO 是什么，为什么 16 字节能通、256 字节会掉

SPI 控制器内部有一小块硬件缓冲（TX FIFO / RX FIFO）：CPU 不必逐字节盯着移位器，写进 TX FIFO 的字节由硬件按时钟发出去；收到的字节先进 RX FIFO，CPU 再取走。



* **16 字节帧能通的本质**：整帧正好塞进 FIFO，从机在整个传输期间不需要再往 FIFO 里补数据，只等时钟走完取 RX。

* **256 字节帧为什么难**：FIFO 装不下 256 字节。从机必须在主机时钟还在跑的同时，一边读 RX、一边把后续应答字节回填 TX FIFO；一旦回填慢了，TX 见底，线上就只能发填充值（表现为后段全 0x00）。

这就是本次所有失败的核心场景：**长帧把 "传输期内持续服务 FIFO" 这件事逼到了台前**，而旧 16 字节测试把它隐藏掉了。

### 4.4 双水位：从机补水下限，主机节拍上限

今天代码里有两个方向相反的 "水位"，容易混在一起：

**（1）从机 TX 水位线 = 14（补水下限）**

从机服务循环每一圈先读状态寄存器里的 TX 占用量 `tfl`；一旦 `tfl < 14`，就一次性把 FIFO 补回到 14 字节。含义是：TX FIFO 里始终保持不少于 14 字节待发，留出被任务抢占时的穿底余量。



* 为什么是 **14 而不是 FIFO 满额 16**：实测写满 16 会丢最早的 2 字节（FIFO 覆盖 / 写错误），14 是这颗 PL022 类控制器上一次可可靠排队的上限。

* 对照 STM32：相当于你在主循环里判断 `SPI_GetTxCount()` 低于阈值就再 `SPI_I2S_SendData()`，只是这里阈值是硬件实测出来的安全值。

**（2）主机时间闸门&#x20;**`due`**（节拍上限）**

早期驱动用 "TX\_FULL 有没有亮"" 已经写了几个 " 判断进度，但实测这颗控制器的 TX\_FULL 在传输期间从不置位，写入数也不能代表线上进度。v7 改成按时间推进：



```
cyc_pb = 每字节硬件周期数 = 主频周期数 × 8 / 时钟频率
due    = min(整帧长, 已过周期数 / cyc_pb + 4)
```

TX/RX 每次都不得超过 `due` 个字节，FIFO 最多只领先线上 4 字节。含义是：**跟着真实时钟节拍走，而不是跟着 FIFO 标志走**，既不会提前把空 FIFO 写穿，也不会落后于线上进度。

一句话区分：从机水位是 "别让桶见底"（保下限），主机闸门是 "别跑得比时钟快"（限上限）。

### 4.5 延迟确认：从机回的是上一帧

协议 v3 采用延迟确认：从机在第 N 帧时钟里回报的 `sid/seq`，是**上一帧有效请求**的会话号和序号。原因是全双工下，主机发请求的同时从机只能用上一次备好的应答回话，来不及在当前这组时钟里现算当前帧。



* 开机空闲帧：`sid=0, seq=65535`。

* 主机第 0 帧注定收不到合格应答（从机还没有有效请求可回），协议把它当同步帧静默跳过，不从 0 开始判失败。

* 主机校验时要求应答序号等于上一帧序号；序号错位也是一种坏帧。

### 4.6 轮询、中断、DMA 三种服务方式

本次从机用的是 **CPU 轮询**：任务循环里反复读状态寄存器，RX 非空就取、TX 有空就补。三种方式的差别：



| 方式     | 做法                             | 本次状态                       |
| ------ | ------------------------------ | -------------------------- |
| 轮询 PIO | CPU 循环读状态、读写数据寄存器              | **当前在用**，占任务循环，频率一高就服务不过来  |
| 中断 IRQ | FIFO 到水位 / 非空时进 ISR 读取或回填      | 未启用；CP 固件原先给 SSP2 挂的中断已被清零 |
| DMA    | 控制器直接在内存和 FIFO 间搬字节，CPU 不逐字节参与 | 3085E 驱动里有双向 DMA 分支，从未启用   |

后续提速最可能动的就是从机服务方式：轮询 → 中断或 DMA。

### 4.7 RTOS 任务、栈和线程阻塞警告



* 503 侧链路是一个独立 OSA 任务：优先级 80，静态栈 4096 字节，收发缓冲 `txbuf/rxbuf` 放静态区，不压在栈上。

* 3085E 侧收发目前占着 shell 线程；日志里反复出现 `Thread shell_uart run time 10~20 ms`，就是 RTOS 报告这个线程单次跑太久。它不影响本轮数据，但长测和提速前应把收发挪到独立任务。

* 轮询循环里不能长时间关中断 / 等 tick，否则系统 tick 不更新、超时判据失效（旧复盘第 21 章补课仍适用）。

### 4.8 0x00、0xFF、错位帧分别说明什么



* **全 0xFF**：总线空闲高电平，从机根本没驱动 MISO（TX 没数据或从机没应答）。

* **全 0x00**：从机 TX 见底后硬件发的填充值，说明应答帧没备够。

* `chk=0`**&#x20;但整帧偏移几字节**：CRC 自洽、图案却整体错位，是相位错位 —— 开头漏了几个时钟，后续字节整体晚 / 早了一格，不是随机噪声。

* 软件缓冲里打印 FF/00，不等于导线上就是该电平；最终定位要靠波形。

## 5. 协议 v3 帧布局与校验判据

公共头：两端 `spi_link_swap.h` 必须**字节一致**（改一端必须同步另一端，建议直接复制）。

### 5.1 帧布局（256 字节）



| 偏移          | 长度  | 内容                           |
| ----------- | --- | ---------------------------- |
| \[0]        | 1   | 方向 magic：主机 `0xA7`，从机 `0xB7` |
| \[1]        | 1   | 协议版本 `0x03`                  |
| \[2..3]     | 2   | 会话号 sid，小端                   |
| \[4..5]     | 2   | 帧序号 seq，小端                   |
| \[6..11]    | 6   | 头部图案                         |
| \[12..13]   | 2   | 头部 CRC16，覆盖 \[0..11]         |
| \[14..253]  | 240 | 载荷图案                         |
| \[254..255] | 2   | 整帧 CRC16，覆盖 \[0..253]        |

### 5.2 图案是纯函数，两端可各自复算



```
swap_pat = magic ^ sid_lo ^ sid_hi ^ seq_lo ^ seq_hi ^ (i * 29)
```

只依赖方向、会话、序号和帧内索引，不依赖随机数。接收端可以不看对端发什么，自己按这个函数算出每个索引**应当出现**的字节，逐字节对比 —— 这就是 v10 能定位 `first=第几字节` 的基础。

### 5.3 校验返回码（`swap_check`）



| 返回码 | 含义                             |
| --- | ------------------------------ |
| 0   | 整帧 CRC、头部 CRC、方向版本、抽查图案全部有效    |
| -1  | CRC 错（整帧或头部）                   |
| -2  | 方向错或版本错                        |
| -3  | 图案错（头部 6 字节 + 载荷首 / 中 / 末三点抽查） |

注意：`-9` 是应用层 "未收满" 的哨兵值，不是 `swap_check` 的返回码。CRC、协议正确、业务成功是三个层次：CRC 过了只代表这一帧没传坏，方向 / 序号对不对要另外判。

### 5.4 为什么加长到 256 字节

帧间间隔和每帧固定开销是按 "帧" 付的，不是按字节付的。旧 16 字节帧实测把时钟从 0.8 MHz 提到 10.7 MHz，总时间几乎不变，说明瓶颈不在时钟而在每帧固定成本。一帧 256 字节把这笔固定成本摊到 16 倍数据上，是当时唯一有效的提速杠杆。块长最终定 256 还是 1024 尚未拍板，`SWAP_SIZE` 单点可调。

## 7. 逐项 BUG 复盘

### BUG-01：CP 固件不按从机角色切方向位

**现象：** `um_spi_init` 只是 72 字节纯转发桩，传入从机角色后，TOP 寄存器的时钟方向 / 帧方向位仍是主机值。

**处理：** 从机分支手写置位 `SCLKDIR`(bit3)、`SFRMDIR`(bit4)，回读确认后再使能 SSE。TOP 位布局：bit0=SSE、bit3=SCLKDIR、bit4=SFRMDIR、bit10=SPO、bit11=SPH；实测从机回读 `0x00062CF8`，Mode 3 两位模式位与主机一致。

**状态：** 已解决。方向位必须手写并回读，不能信任 SDK 转发。

### BUG-02：256 字节从机传输期服务不过来

**现象：** v3 早期固定形态 —— 从机只收到 48\~158 字节，主机后段全 0x00；频率越低 / 帧越长越明显。

**判读：** FIFO 装不下 256 字节，从机必须在时钟跑的同时持续回填 TX、读取 RX；轮询循环一旦被抢占或圈速不够，TX 见底就发填充值。16 字节帧整帧进 FIFO，掩盖了这个需求。

**状态：** 部分缓解（水位 14 + 节拍闸门把 200k/400k 拉通）；根因服务方式仍是轮询，800k 下依然脱链。

### BUG-03：把 FIFO 标志和写入数当成进度判据

**现象：** v4 探针发现本控制器 TX\_FULL (bit5) 传输期间从不置位；`tx` 计数冲到 62 而 `rx` 才 2；`bc`(0x10) 恒等于写入值，不是剩余计数。

**结论：** 不能用 "写了几个""FIFO 满没满 " 判断线上进度；真正完成判据是状态位 TX\_EMPTY 且非 BUSY。进度推进改由 v7 时间闸门承担。

**状态：** 已解决（判据层面）。

### BUG-04：主机推进与线上时钟脱节

**现象：** 早期循环只盯 RX 收发满就退出，尾部字节没写完；TX 写入数不代表发送完成。

**处理：** v7 按已过周期数算 `due`，TX/RX 都不超过 `due+4`；v6 加物理时间地板，没走满物理时长不返回。

**状态：** 已缓解。主机 `xfer` 仍恒为物理下限 2 倍（见 BUG-10）。

### BUG-05：上一帧残留字节污染新帧

**现象：** 帧头可能读到上一帧尾巴，造成整帧错位 / 回绕。

**处理：** v9 在每次主机事务开始前倒空 RX FIFO（上限 64 字节）。

**状态：** 已解决。

### BUG-06：回填水位取值

**现象：** 水位低了容易穿底，水位高了在抢占窗口内更危险；实测 FIFO 一次写满 16 会丢最早 2 字节。

**结论：** 安全水位定 **14**（`SWAP_PRELOAD=14`）；v3n 的 13 余量不足，v3o 的 14 实测可用。

**状态：** 已解决，14 是实测上限，不要再往上加。

### BUG-07：错位是累积性的，收满再校验纠不回来

**现象：** 20:45 解剖：BAD#1 帧头 8 字节又出现在 248 处（整帧错位 / 回绕）；BAD#2 从头就是载荷，一个头部字节都没有。错位一旦发生，后续字节整体错下去，靠 "收满 256 再校验" 永远纠不回来。

**处理（v3p，三处）：**



1. 帧头重同步状态机 `hs`：0 = 没见到 magic，除 `0xA7` 外全当杂字节丢弃；1 = 已见 `0xA7`，等版本字节 `0x03`；凑齐才算帧首。

2. 超时判据从 `got` 改成 `seen`（总线真实读走的字节数）：同步阶段 `got` 停在 0/1，但总线一直在来字节，用 `got` 会把 "正在对齐" 误判成 "主机走了"。

3. RX 排空仅在 `seen!=0` 时执行：`got==0` 那轮 FIFO 里可能正躺着刚到的帧头，主动排空等于丢掉帧首。

**状态：** 重同步方向有效（帧头能重新对齐），但 corruption 仍打在中段 / 尾部，**不是根因**。

### BUG-08：失败后从机挂死，重启才恢复（含一次被推翻的误判）

**现象与经过：**



* 20:51 一次 812.5k 失败后，21:00 跑 100k/200k，主机 MISO 全 `0xFF`，COM6 全程只有 ALIVE 心跳，一个 `SLAVE SWAP` 都没有。当时据此怀疑 "低档位分频 / 模式有问题"。

* 21:11 重启后同一档 200k 立刻 300/300 干净通过。

**结论：** 21:00 的全 FF 是**从机被上一次失败挂住后的残留状态**，不是频率或分频问题；"低速率收不到" 的判断作废。失败后从机状态（FIFO、txw、帧头相位）会失步，同会话内重发救不回来，需要重启从机重新武装。

**状态：** 现象已确认；挂死的具体寄存器 / 状态路径未单独定位。

### BUG-09：频率扫频 —— 三档三种表现

干净重启后实测（300 帧 / 档，详见第 10 章）：



| 频率        | 字节间隔    | 结果                                            | 失败形态                                           |
| --------- | ------- | --------------------------------------------- | ---------------------------------------------- |
| 200 kHz   | 40 µs/B | 两轮 300/300，后又 1000/1000，0 重发                  | 无                                              |
| 400 kHz   | 20 µs/B | 300 帧靠重发兜底通过，1 帧中途错位 `first=112`，从机 `txw=249` | 中段局部错位                                         |
| 812.5 kHz | 10 µs/B | 帧 1 即挂，连续两轮复现                                 | 全 0x00 / 短帧 232\~231 字节 / `chk=0 first=2` 相位错位 |

**结论：** 瓶颈随字节间隔缩短而暴露：200k 服务窗口宽裕；400k 个别帧赶不上；800k 轮询循环在传输期内跑不完，帧头后脱链。抬主机频率不能越过从机服务能力。

### BUG-10：主机 xfer 恒为物理下限 2 倍（未定位）

**现象：** 各档 `xfer` 实测正好是 `256×8/标称频率` 的 2 倍：200k 物理 10.24 ms /xfer 20 ms；400k 5.12 / 10 ms；800k 2.53 / 5 ms。

**存疑点：** `CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC=32000000`，但 `k_cycle_get_32` 实现在 BSP 侧、不在 Zephyr 树内，真实计数速率未核实；v6 地板与 v7 节拍都建立在这个常数上。高度怀疑实际线上 SCLK 只有标称一半，或周期常数算错一倍。

**状态：** 未定位。这是 "不抬频率也可能白拿一倍" 的直接抓手，但需要先量一次周期计数 / 波形才能下结论。

### BUG-11：计数口径与探针遗留



* 400k 结束行 `ret=0` 而 total `retries=2`、从机 `bad=1`：两端重发 / 坏帧计数口径没完全对齐。

* 从机 `tmin/dry` 探针：帧尾正常排空也会计数，**不能区分中途穿底和帧尾排空**；真要复用需改成 "`tfl==0 && txw<SWAP_SIZE`" 才计一次。

* 从机 `ok` 偶尔比帧数多 1（含同步帧），属口径现象，不影响 `bad=0` 判读。

* `demo_spi.c` 里 `sse_lost` 计数器、临时脚本 `brace_check.py` 属可清理残留。

### 8.3 两端函数调用顺序图

下图是**运行时调用链**，不是修改工程的顺序；`CONFIG_*`、设备注册、命令表属于编译期配置，不在逐帧链路上。

**3085E 主机侧（命令触发，占用 shell 线程）：**

```text
用户串口输入 app spi2swap [count] [gap_ms] [freq]
└─ Shell 按命令注册找到 shell_spi2swap()                 [system_app_shell.c]
   ├─【参数与设备准备】
   │  ├─ 校验 argc / count / gap / freq（超范围直接 -EINVAL，不配硬件）
   │  ├─ device_get_binding(CONFIG_SPI_2_NAME)           ── 失败 -ENODEV
   │  ├─ 产生非零 sid；sys_wake_lock + k_msleep(gap_ms)
   │  └─ 静态缓冲 s_swap_tx / s_swap_rx（256 B，不压 shell 线程栈）
   └─【逐帧循环 i = 0..count，实际发 count+1 帧】
      └─【本帧重发循环，最多 2 次】
         ├─ swap_frame(tx, MASTER, sid, i)              [协议头：装帧 + 图案 + 两处 CRC]
         ├─ memset(rx, 0xa5, 256)                      [预填缓冲，便于观察覆盖情况]
         ├─ spi_transceive(dev, &config, &ts, &rs)      [Zephyr SPI API]
         │  └─ 驱动主机等长双向分支                       [spi_acts.c 约 797 行]
         │     ├─ 校验 tx/rx 非空、等长、chunk>0
         │     ├─ 开 TX/RX FIFO；帧前清空 RX FIFO（上限 64 字节）
         │     ├─ spi_acts_write_read_data_by_cpu(..., frequency)
         │     │  ├─ cyc_pb = 主频周期×8/freq；due = elapsed/cyc_pb + 4（时间闸门）
         │     │  ├─ TX 内层：tx_len<due 且未满 → 写 TXDAT
         │     │  └─ RX 内层：rx_len<due 且非空 → 读 RXDAT
         │     ├─ 物理时间地板：未走满 chunk×8/freq 对应周期数不空返
         │     ├─ 等 TX_EMPTY 且非 BUSY（10 ms 超时 -ETIMEDOUT）
         │     └─ 失败：acts_reset_peripheral + ctx->config=NULL；成功才推进游标
         ├─ swap_check(rx, SLAVE) + 序号校验（应答 sid=sid、seq=i-1）
         │  ├─ 合格 → frame_ok，跳出重发
         │  ├─ i==0 同步帧 → 静默跳过，不重发
         │  └─ 不合格 → 复算 s_exp 逐字节比对（ndiff/first + 尾部双 dump）
         │        tries>=2 → -EIO；否则 ++retries、k_msleep(gap_ms) 后重发
      ├─ 汇总 SPI SWAP total / frames / retries
      └─ sys_wake_unlock；打印 PASS/FAIL good=count/count ret=retries
```

└─ spi_link_test_start()                                 [demo_spi.c]

| 812.5 kHz | 脱链，未完成  | —           | 2.53 ms  |

### 10.3 失败解剖样例（v10 逐字节定位）



* `first=236`，ndiff=20/256：尾部区局部错位，收到数据整体晚 2 字节 / 多 2 字节前缀。

* `first=0`，ndiff=253/256，全 `0x00`：从机 TX 没数据，硬件填充。

* `chk=0`，`first=2/4`，ndiff≈251：CRC 自洽但整帧偏移，字节呈 ±1 抖动，相位错位；`chk=0` 说明是成片规律性错位，不是随机噪声。

* 短帧 `got=231/232/234`（`chk=-9` 未收满）：RX 没读满整帧。

## 11. 结论边界与尚未证明的事

### 11.1 已实测证明



* 3085E 主机 / 503 从机的 256 字节双向帧，在 200 kHz 下 1000 帧无坏帧、无重发。

* 400 kHz 下个别帧会中途错位，重发兜底可救；800k 下从机轮询服务跟不上，帧头后脱链。

* 14 是 503 TX FIFO 一次可可靠排队的水位上限；TX\_FULL 与 `bc` 不能作完成 / 进度判据。

* 失败后从机会进入失步挂死状态，重启可恢复。

### 11.2 尚未证明 / 存疑



* 主机 `xfer` 2 倍开销的根因：周期常数 32 MHz 是否与实际主频相符未核实；线上真实 SCLK 频率未用波形量过。

* 3085E ACTS SPI 主机侧 FIFO 实际深度（驱动里 `SPI_FIFO_LEN=64` 是约定值，不是实测深度）。

* 3085E 双向 DMA 路径从未启用；能否靠 DMA 把从机 / 主机服务压力降下来未验证。

* 503 EVK 模组脚 30\~33 是否挂板载 codec，无原理图确认。

* 503 作从机的精确时钟上限：13 MHz 过、26 MHz 挂，中间未细扫；812.5k 已验证脱链。

* 块长最终 256 还是 1024 未拍板；1000 帧以上长测、跨重启复测、温度 / 电压变化后的稳定性未覆盖。

* 400k 重发兜底的长期失败率没有多轮统计；业务文件传输尚未接入。

* 技术负责人所说 "不够快" 具体指延迟、吞吐还是传大文件，提速目标值 / 验收标准未定。

### 11.3 不能外推的结论



* 本文结论只对应当前两块板、当前固件与接线；不推断其他模组版本或原厂 AT 固件具有相同能力。

* 00/FF 软件读数不能单独作为线上电气故障证据，必须结合波形。

## 12. 下一步建议

**短期（稳）：**



1. 稳定基线定 **200 kHz**；再隔几分钟补一轮 1000 帧复测，确认跨会话稳定。

2. 400k 作为 "带重发兜底的实验档"，先多跑几轮统计真实重发率，再决定是否作为备选工作点。

**中期（定位 2 倍开销）：**

3\. 先量一次 `k_cycle_get_32` 周期计数与线上 SCLK 波形，核实 32 MHz 常数与分频是否差一倍；这是不抬频率也可能拿回一倍速度的抓手。

4\. 核对主机驱动完成等待段，区分 "物理移位时间" 和 "软件等待 / 线程调度时间"。

**提速（动从机服务方式）：**

5\. 把 503 从机从轮询改为 SSP2 RX/TX 中断驱动：FIFO 到水位进 ISR 读取 / 回填，缩短传输期服务延迟。

6\. 评估 3085E 双向 DMA 路径；把收发从 shell 线程挪到独立高优先级任务，消除 `shell_uart run time` 阻塞警告。

7\. 块长是否抬到 1024，待服务方式稳定后再用 `SWAP_SIZE` 单点验证。

**不建议：** 继续单纯抬高主机频率越过从机服务能力；在没量波形前改分频常数；把 PCM\_DIN/DOUT 丝印方向当 SPI 方向换线。
