九、函数头采用 STM32 标准外设库风格

今后新增或更新函数声明、定义的函数头时，必须用半角空格将标签、参数名和说明正文分成三列，分别左对齐。同一函数头内，第一列按最长标签留位，第二列按最长参数名留位。说明跨行时，续行从第三列开始。

`@param` 的参数名写在第二列，参数说明从第三列开始。`@brief`、`@retval` 和 `@note` 留空第二列，说明从同一第三列开始。`@retval` 的返回值（如 `0`）是说明的开头，也写在第三列。

以 UMA503 的 `getaddrinfo_with_netif` 为例。

```c
/**
 * @brief              根据主机、服务和地址约束取得可连接的地址列表。
 * @param  nodename    主机名或数值地址字符串。
 * @param  servname    服务参数，HTTPS 使用十进制端口字符串。
 * @param  hints       可选输入，用于限定地址族、套接字类型及协议。
 * @param  res         输出指针，用于接收结果链表。使用结束后调用 freeaddrinfo 释放。
 * @param  netif_name  用于本次查询的网络接口名称。
 * @retval             0 表示解析成功，非零表示失败。
 * @note               结果链表中的地址指针在释放链表后失效。
 */
```

具体要求：

1. @brief 说明整体作用，不要只复述函数名。

2. 每个参数都要解释用途，并区分输入、输出和输入输出。

3. 长度、数量、时间和频率参数应说明单位。

4. 指针参数应根据接口实际约定说明：

- 指向的数据；
- 缓冲区长度；
- 可读或可写要求；
- 是否允许为空；
- 必要时说明对象生命周期和内存所有权。

5. 返回状态码的函数，应解释各个实际返回值，不能只写“返回执行结果”。

6. 无参数时保留 `@param`，无返回值时保留 `@retval`。这两种情况均将第二列留空，在第三列写“无”。

7. @note 根据实际情况说明：

- 调用前需要完成的初始化；
- 是否阻塞及超时条件；
- 是否允许在中断中调用；
- 是否访问硬件寄存器；
- 是否存在并发或临界区限制；
- 重要的副作用及调用顺序。

8. 不要编造接口没有保证的行为。

9. 头文件中的函数声明也要说明函数作用、参数和返回值。
   声明与实现的说明必须一致，实现处可以补充内部流程和设计原因。

10. 函数指针和回调类型应说明调用方、触发条件、参数及返回值约定；只能说明已核实的行为。

11. 关键入口要在函数头写清“谁调用它、成功或失败后去哪”。
    给出真实的调用点、回调表项或任务名称，例如“由 Shell 表项 `SHELL_CMD(spi2http, ...)` 分派”“返回 0 后进入逐块握手”。
    没有调用者信息的内部辅助函数不必强写，一句职责说明即可。

12. 间接入口要写清触发方式，不能只写函数名。
    例如 `spi_acts_init()` 由 `DEVICE_DEFINE` 登记，Zephyr 到 `POST_KERNEL` 阶段经 `entry->init(dev)` 调用；
    Shell 命令写明表项和 handler；任务写明由谁创建、被什么事件唤醒。
    这类入口在源码里搜不到显式调用，注释是读者唯一的线索。

13. 成功与失败写到实际负责的那一层。
    只是透传底层错误时，说明错误向哪一级传递即可，不必罗列每个错误码。
    存在资源借用、状态锁定或统一清理时，指出真正归还它们的位置，例如“由 `close` 的调度收回”。

十、函数内逐行解释

1. 对处理范围内的有效代码语句逐行过一遍，逐条判断是否需要说明。
   需要解释的按本节和第十一节写，明显可读的语句按第十五节第 1 条豁免，不硬凑注释。

2. 变量定义说明用途，初始化说明初始值的意义。

3. 条件判断说明判断依据，以及进入该分支的原因。

4. 循环说明处理对象、结束条件和必要的超时机制。

5. 函数调用说明它在当前流程中的作用。

6. 返回值、错误码和 goto 说明触发原因及后续处理。

7. 寄存器读写说明访问目的、相关字段和必要的时序要求。

8. 对计数器、状态变量和标志位，说明它们在当前阶段表示什么，以及何时更新。

9. 不要求给单独的花括号、空行添加无意义注释。

10. 跨多行的同一条语句，按照逻辑整体解释。
    续行存在独立含义时，再补充说明。

11. 已由上方功能块注释完整解释的入口语句，不必在行尾重复同一句话。

12. 避免空泛注释，例如：
    “调用函数”“进行判断”“定义变量”“执行循环”。
    必须解释当前代码的具体用途。

十一、按功能划分代码块

1. 同一个函数内部，按照实际功能划分代码块，例如：

- 参数检查；
- 状态和计数器初始化；
- 配置或启动外设；
- 写入发送 FIFO；
- 读取接收 FIFO；
- 等待发送完成；
- 检查异常状态；
- 清理资源并返回。

2. 同一阶段的变量声明、初始化和准备数据的赋值可以连续书写。这一组结束后，与接下来的参数检查、分支、循环、函数调用或其他业务处理之间必须恰好留一行空行。函数开头和嵌套块内部都遵循此规则，即使只声明了一个局部变量。

3. 不同功能块之间恰好留一行空行。同一功能块内，没有独立上方注释的连续业务语句可以紧接书写。普通声明组后若紧接一组受 `#if`、`#ifdef` 或 `#ifndef` 控制的声明，即使分支内只有一个变量，两组之间也要空一行。`#endif` 与下一段业务之间同样空一行；下一段有上方注释时，空行放在注释之前。

4. 独立成行的注释紧贴它所说明的代码，与代码缩进一致，中间不留空行。前面已有代码时，前一段代码与注释第一行之间恰好留一行空行。单条语句的说明和整个功能块的说明都遵循此规则。声明组后紧接功能块注释时，两条规则共用同一行空行。

5. 功能块的整体说明放在入口语句正上方，解释这一阶段的目的。行尾注释用于补充具体语句的含义。

6. `if(...)`、`else if(...)`、`else`、`for(...)`、`while(...)` 和 `switch(...)` 的左花括号必须在控制行的下一行独占一行，右花括号也必须独占一行。关键字与左圆括号之间不留空格。正文从左花括号的下一行开始，缩进一级。`do` 循环同样将花括号独立成行，末尾的 `while(...);` 写在右花括号的下一行。

7. 每个分支和循环体都必须写出成对的 `{}`，即使正文只有一条语句。`else if(...)` 和 `else` 必须写在上一分支右花括号的下一行。各分支分别加花括号，不能把条件、正文或相邻分支压在同一行。

8. 分块只调整排版。补齐控制体花括号时先核对原有嵌套关系，保持语句顺序及分支归属。不要为划分功能块额外引入作用域。

9. **普通代码和条件编译按同一套层级缩进。**  
   同一层的声明、业务语句和预处理指令从同一列开始。文件顶层从最左列开始，进入函数体、控制体或条件编译分支就缩进一级，嵌套时逐层累加。  
   同一组 `#if`（含 `#ifdef`、`#ifndef`）、`#elif`、`#else` 和 `#endif` 的 `#` 必须在同一列。缩进加在 `#` 前，指令写作 `#if`、`#endif`。  
   各分支内的语句和指令比本组 `#if` 深一级。遇到 `#endif` 回到本组起始列，后续同层业务代码与之对齐。相邻的独立条件编译块之间恰好留一行空行。

10. **一条语句优先写在一行。**  
    函数签名、带实参的调用、赋值和条件表达式，只要单行能读清就完整写在一行。整理时可将原先拆开的短调用合回一行，保留参数顺序。  
    先按代码本身判断是否需要折行。若移走行尾注释后仍难以读清，可在参数之间或子条件之间折行，续行与同组内容对齐。控制体花括号仍按第 6 条独占一行，宏续行按第十二节第 12 条处理。

11. **同一功能块内连续赋值时，优先将等号列对齐。**  
    同一缩进层级上连续几行给变量或结构体成员赋值，以组内最长的左侧表达式为基准，在较短项后补半角空格。最长项与 `=` 之间留一个空格，每行 `=` 后也留一个空格，让右侧取值从同一列开始。连续几行带初值的变量声明也可按此方式排列。  
    链式赋值只对齐每行第一个 `=`，后面的 `=` 两侧各留一个空格。遇到空行、分支或新的处理阶段，下一组独立确定列位。行尾注释按第十二节另行对齐。

十二、行尾注释对齐

1. 同一个函数内部，所有行尾注释的“/*”起始位置必须位于同一列。

2. 对齐位置以该函数中需要行尾注释的最长代码行为基准，计入缩进，在最长代码之后至少留 4 个空格。

3. 同一个函数即使分成多个功能块，也必须使用同一个行尾注释对齐列，不能每个功能块各自对齐。

4. 使用空格对齐，不要混用 Tab 和空格。
   先按第十一节确定代码和预处理指令的缩进，再用代码与行尾注释之间的空格对齐注释。

5. 宏定义按照连续的相关宏定义组统一对齐，以该组最长代码为基准。

6. 全局变量、结构体成员、枚举成员等，分别在各自声明组内统一对齐。

7. 不要求整个文件中的不同函数使用同一个对齐列，各函数可以根据自己的最长代码确定。

8. 功能块上方的独立注释，与代码缩进对齐，不参与行尾注释列对齐。

9. **代码单行清晰、加上行尾注释才过长时，优先将整条注释移到代码正上方。**  
   若一条长语句会把全函数的行尾注释列推得过远，也把该句的说明上移。上方注释与语句同缩进并紧贴语句，前面已有另一段代码时空一行。需要多行才能讲清的说明可在注释内换行，其余行尾注释仍按第 2 条对齐。

10. 只要求行尾注释的起始位置统一，不要求为了对齐结尾的“*/”填充大量空格。

11. 不要为了缩短对齐列而擅自拆分或重排代码语句。

12. 特别注意宏续行：
    不能在续行反斜杠后追加内容，不能破坏预处理语义。
    多行宏不适合安全添加行尾注释时，使用上方独立注释。

`uart_rx_handle()` 的声明区中，`new_data` 在所有配置下都使用，`smp` 只在启用管理协议时才声明。两组声明之间留一行。

```c
    uint32_t rd_len;
    bool new_data = false;

    #ifdef CONFIG_MCUMGR_SMP_SHELL
        struct smp_shell_data *const smp = &sh_uart->ctrl_blk->smp;
    #endif
```

同一函数的接收循环中，`ring_buf_put_claim()` 的三个实参可以一行读完。较长的缓冲区说明紧贴在调用上方。

```c
        /* 以环形缓冲区总容量作为申请上限。data 接收连续可写区的起始地址，len 是本轮实际可写的字节数。 */
        len = ring_buf_put_claim(sh_uart->rx_ringbuf, &data, sh_uart->rx_ringbuf->size);
```

十三、注释深度

请面向“了解 STM32 基础开发，但第一次接触当前芯片和 SDK”的读者解释。

遇到相关代码时，补充以下必要知识：

1. SDK 接口、驱动接口和底层寄存器操作之间的关系。

2. 板级引脚复用、设备初始化和应用调用之间的关系。

3. FIFO、数据寄存器和移位寄存器的区别。

4. 轮询、中断和 DMA 在当前代码中的实际作用。

5. SPI 全双工传输与发送、接收数据之间的关系。

6. 临界区保护的对象，以及为什么某些等待操作不能放在临界区内。

7. 内存屏障、volatile 和寄存器回读各自的作用与限制，不能把它们混为一谈。

8. 操作系统 tick 与实际时间的换算依据。

9. 任务、回调、设备对象和函数指针之间的调用关系。

10. 错误处理、资源释放和状态恢复的流程。

11. 相比 STM32 常见写法，当前 SDK 将哪些工作放到了板级配置、驱动层、操作系统或应用层。

12. 缓冲区归属：一个缓冲区由谁写、谁读、何时可以被覆盖，写在首次交接或最关键的边界处。
    双槽、环形这类会被硬件自行复用的区域，必须说明“软件处理 A 槽时硬件在写 B 槽”这类并行关系。

只解释与当前代码有关的知识。

较长说明放在函数头或功能块上方，不要把整篇教程堆到每一行后面。
STM32 类比必须落到具体寄存器或位，并能反过来指导读代码；只写“类似某个 HAL 函数”属于缺乏依据的类比，宁可不写。
本节的结论同样受第十六节第 5 条约束，需要标注可追溯的来源。

十四、执行方式

1. 先确认 Git 范围及实际依赖，再建立文件覆盖清单。

2. 按文件或模块分批完成，保持统一的注释风格。

3. 发现新的实际依赖时，更新清单并继续处理。

4. 文件数量较多时，可以分批推进，但不能擅自将任务缩减为：

- 只注释关键函数；
- 只注释新增代码；
- 只注释 Git 修改行；
- 只处理 .c 而忽略 .h；
- 只处理被引用的声明而忽略文件其余内容。

5. 在没有实质性歧义的情况下持续执行，不要每处理完一个文件就停下来请求确认。

十五、注释落在哪一层

**一条信息只在最合适的那一层讲一次。** 同一事实在函数头、块注释和行尾各写一遍，等于三处都要维护。

| 位置 | 该让读者看到什么 |
|---|---|
| 文件开头 | 本文件负责哪段流程，主入口在哪，和哪些模块交接 |
| 关键函数开头 | 进入条件、谁调用、成功后去哪，以及读代码必需的参数或资源约定 |
| 功能块正上方 | 一句动作标题；必要时补关键顺序、状态变化或原因 |
| 难懂的单条语句上方 | 这一行改变了哪项硬件或协议状态，为什么必须在这里做 |
| 行尾 | 只留单位、位号、字段含义或极短的局部约束 |

1. 普通赋值、明显的自增、简单转发和一眼可见的返回直接读代码，不必逐行加注释。
   遇到不明显的初值、特殊错误判断或隐蔽副作用，才补说明。

2. 阶段划分跟着实际步骤走，名称用动词短语。函数头路线与块注释都只写动作名，不互相抄写细节。

3. 行尾注释只承担短信息。解释需要两行以上时上移到语句正上方，不靠大量空格把注释列推到屏幕右侧。

4. 一个约束、一次所有权交接、一条超时规则，只在首次交接或最关键的边界处写清。
   后文再提到时写“同第 N 阶段”，不重复展开。

5. 注释密度由每段的阅读难点决定，不由行数决定。难度低的连续语句可以整段无注释。

十六、功能块注释必须写满三层

1. 每个功能块上方必须有独立注释，不能用行尾注释代替。
   只有行尾注释的函数视为未完成，即使每行都写得很准确。

2. 块注释固定写三层，缺一层即为不合格：

- 这一阶段在做什么（动作本身）；
- 硬件或协议上意味着什么（哪个寄存器、哪一位、哪块缓冲、什么时序）；
- 不做、做错或失败会怎样（现象、错误码、由谁回收）。

3. 超过 40 行的函数，用“阶段 N｜动作”给块命名，并在函数头的 `@note` 列出阶段清单。
   跨函数引用时用编号对应，例如“`close` 的第 2 阶段回收 `open` 的第 6 阶段状态”。

函数头的清单是扫读入口，块注释是分段正文，两处编号必须一一对应。以下是 `spi_acts_spi2_circular_open()` 的写法。

```c
/**
 * @brief          取得 SPI2 总线并启动跨帧持续工作的接收环。
 * @param  dev：   [输入]已绑定的 SPI2 设备对象，非空，由设备模型持有。
 * @param  config：[输入]非空，主机、Mode 3、8 位、硬件片选 0，请求 100 kHz～8 MHz。
 * @retval 0       表示可收发，负值为各阶段返回的错误码。
 * @note           阶段 1 参数与平台校验 → 2 会话互斥 → 3 平台自检 → 4 绑定 DMA 控制器 → 5 拿总线锁
 *                 → 6 建立会话状态 → 7 总线静音 → 8 申请 RX/TX 通道 → 9 配置时钟与格式 → 10 切换 DMA 通路
 *                → 11 描述双槽接收环 → 12 下发通道配置 → 13 回读重载位 → 14 启动 RX；失败统一由阶段 15 回收。
 */
int spi_acts_spi2_circular_open(const struct device *dev, const struct spi_config *config)
{
    ...

    /* 阶段 1｜参数与平台校验：只接受主机 + Mode 3 + 8 位 + 硬件片选这一种组合，校验全部在碰寄存器之前完成。 */
    if (!dev || !config || config->operation != ...)
    {
        return -EINVAL;
    }

    /* 阶段 7｜总线静音：关掉收发请求并保持片选无效，避免申请通道和写 DMA 描述的这段时间产生 SPI 时钟。 */
    spi->ctrl &= ~(SPI_CTL_RX_DRQ_EN | SPI_CTL_TX_DRQ_EN | SPI_CTL_WR_MODE_MASK);
    spi->ctrl |= SPI_CTL_SS;

    ...

fail:
    /* 阶段 15｜统一回收：active 已在阶段 6 置位，close 能处理“通道只领了一半、FIFO 只开了一半”的半成品状态。 */
    (void)spi_acts_spi2_circular_close(dev);
    return ret;
}
```

编号规则：

- 从 1 连续编号，不跳号，不超过两位数。
- `@note` 的箭头清单超出一行时，续行与上一行的“阶段”对齐，不另起缩进层级。
- 失败路径单独占一个编号，放在函数末尾，不与正常流程混编。
- 阶段名用“动词 + 对象”，写成“参数与平台校验”“申请 RX/TX 通道”，不写“第一部分”“初始化”这类无法定位的说法。

4. 涉及寄存器写入的语句，注释必须给到四件套：寄存器名、位号、位名、置 1 与清 0 各自的含义。
   例：“读 RX 通道 CTL 的 bit18（`SPI2_CIRC_RELOAD`），为 0 表示硬件重载未使能”。

   位号只在这一位确实影响理解或排查时才写到编号。
   只改变使能状态、不参与完成判断的位可以只写位名；但不能含糊成“设置某个位”，让人无法定位。
   位号、复位值都要先查实际宏或手册，不凭经验填。

5. 结论必须可追溯，按三档标注，标在功能块注释的硬件含义那一层，不写在行尾。

- A 档｜仓库内可定位：优先写符号名，必须能检索到。
  例：“依据：`DMA_CTL_RELOAD` 定义于 `pdma_acts.c:46`，值为 `0x1 << 18`”。
  宏名、函数名、结构体成员名比行号稳定，代码一改动行号就漂；只有符号不便定位时才单独写“文件:行号”。
- B 档｜仓库外资料：只写资料名与章节或寄存器名，不写页码。
  例：“依据：ATS3085x 用户手册《DMA》章 通道控制寄存器”。
- C 档｜推断：显式写“（推断，未核实）”，改用“据……推测”句式，禁止写成确定事实。

  同一事实只标一次；一个函数里多处同类依据，合并进函数头 `@note` 的“依据”行。
  禁止编造页码、文件名、章节号。给不出可定位来源时改用代码自证：写出对应宏或定义名，让读者能自己检索到。

6. 涉及常量的语句必须写出来源与含义。
   例如 `0xff` 表示任意通道，`SPI2_CIRC_BYTES = 512` 是一次片选的数据量，`CONFIG_SPI_2_DMA_ID = 9` 是外设请求号而不是通道号。

7. 错误分支必须写“触发条件 + 后果 + 清理方”。
   只写“返回错误码”不合格。

8. STM32 类比规则：一个功能块最多一句，且必须落到具体寄存器或位，例如“等价 `DMA_SxCR` 的 `CIRC` 位”。
   禁止成段教程，无法核实的对应关系不写。
   只写“类似某个 HAL 函数”属于缺乏依据的类比。

十七、完成后的检查与交付

完成后逐项检查：

1. 范围检查：
   Git 初始文件及已确认的实际依赖是否全部进入覆盖清单。

2. 整文件检查：
   每个已纳入文件是否完成全部代码的注释整理，而非仅修改区域。

3. 中文检查：
   英文技术说明是否已翻译。
   版权、许可证和必须保留的工具标记除外。

4. 函数头检查：
   函数作用、参数、返回值及必要注意事项是否完整。标签、参数名、说明是否分别左对齐，返回值和续行是否从说明列开始。

5. 逐行检查：
   有效语句是否得到解释，是否存在仅复述语法的无效注释。

6. 分块与控制结构检查：
   声明、初始化或准备数据的赋值结束后，与后续业务逻辑之间是否恰好留一行空行，嵌套块内是否同样处理。
   独立注释与前一段代码之间是否恰好留一行空行，注释是否紧贴被说明的语句或功能块并与其缩进一致。
   逐个检查分支和循环，包括只有一条语句的控制体。花括号是否齐全且各自独占一行，`else if`、`else` 是否紧接在上一分支右花括号的下一行。

7. 对齐检查：
   同组连续赋值的首个 `=` 是否对齐，链式赋值和后续功能块是否保留各自的间距。
   同组条件编译指令的 `#` 是否与所在层的普通语句同列，分支正文是否再缩进一级，嵌套结束后是否回到对应外层。
   可单行读清的语句是否完整保留在一行；若加上注释才过长，是否已将注释上移，并保持其余行尾注释同列。
   宏定义及其他声明组是否分别统一对齐。

8. 技术准确性检查：
   是否存在注释与代码不符、单位错误、类型来源错误、调用关系错误或未经验证的硬件结论。

9. 修改边界检查：
   比较修改前后的有效代码，核对补括号处的条件、受控语句、循环体边界和 `else` 归属，确认程序行为未改变。
   特别检查字符串、预处理指令、宏续行和条件编译。

10. 文件格式检查：
    编码和换行格式是否保持，是否产生无关差异。

11. 构建验证：
    有可用构建环境时，执行与涉及文件相对应的构建验证。
    某个构建未覆盖的条件分支不能声称已经验证。
    没有验证条件时如实说明，不得声称编译通过。
