# ATS3085E + UMA503 网络功能迁移基线

整理日期：2026-11-25　｜　对象：`D:\CAT1.bis_OpenCPU-main-sample-20261118`（参考 A）、`D:\ZS302A`（参考 B）、当前 `D:\ats3085e` + `D:\UMA503\UMA503-V7_OPENCPU_OC_2025.03.14_1644`

## 0. 结论先行

1. **两个参考工程是两套相反的分工，不是同一套方案的两种写法。**
   - ZS302A：CAT.1 模组只当"管道"（SPI 命令收发 + 网络），**云端协议解析、签名、状态机、幂等全在主控**。
   - CAT1 sample：**模组自己完成注网→对时→MQTT→HTTP 会话→业务判定**，主控只发指令、收结果。这一套才是"服务器下发全部由网络侧处理"的现成样板。
2. **当前 3085+503 处于"管道已通、业务未迁"的中间态**：503 有注网、TLS、HTTP 执行器、MQTT 登录订阅；3085 有完整的 P4 上传状态机（签名、分片、对账、complete）。真正被搬过去的只有传输层，业务决策仍全在 3085。
3. **迁移的真实工作量不在网络，在"业务语义"**：需要把 ZS302A 的 `src/onenet/*` + `src/cloud/*` 那一层搬进 503，并把 SPI 从"原始 HTTP 请求执行器"升级为"业务动作 + 数据块 + 结果"。现成的执行器（`spi_link_https.c`）可以直接复用，不必重写。

### 2.2 三条数据链

**A. 遥测属性链（上行）**

```
电量/充电/录音状态/绑定/剩余容量（getter 实时取）
  → cloud_task 组 OneJSON（1 s/批，静态缓冲 pkt/data/val）
  → cloud_iot_publish()（唯一出口）
  → cloud_4g_send() → txq(深2) → 0x50
  → 模组 MQTT PUBLISH → 平台
```

断链时 IOT FSM 进 `T3 SUSPEND`，恢复后回 `T2`；连续失败 ≥3 进 `T4 ERROR` 再回 `T0`。

**B. 录音文件上传链（上行 + 回执）**

```
录音库写盘 /SD:/NORMAL/YYYYMMDD/HH_MM_SS.msbc（东八区命名）
  → 扫描新增文件、等文件"封口"（size 稳定，否则 -EAGAIN）
  → nt26_get_file_md5_size()：采样 MD5 + 真实长度
  → localFileId = YYYYMMDDHHMMSS（由录音起始 UTC 纯算术推出，零目录操作）
  → POST /multipart/init（4 头签名；body: localFileId, fileMd5, fileSize, durationMs,
       audioFormat, contentType, originalFileName, recordedAt, partSize, uploadSignVersion=V2）
  → 响应取 objectKey / uploadUrl / 分片范围
  → 逐片 PUT（0x63/0x64/0x65，0x67 NAK 原样重传，按服务器给的 offset/len 读文件）
  → POST /multipart/complete（同会话）→ PUT 2xx 后再 POST /complete（5 字段）
  → 判 status=00000 && syncStatus=SYNC_SUCCESS
  → 上报 event_file_sync_record；失败重试 1 次（换新 ts/nonce 重签），耗尽仍上报 file_sync
```

关键工程约束（都是踩过的坑）：
- 预签名 URL 440 B + PUT 头 80 B > 514 B 帧 → cJSON 组包 -28，**PUT 从未发出**；改用 V2 短 URL（约 270 B）。
- complete 放弃时必须置 `last_path`，否则下轮云端短路返回 `SYNC_SUCCESS`（无 uploadUrl），`WAIT_SESS` 5 s 超时死循环。
- 上传门控要求 `net && file==FILE_READY`，唯一 driver 是 `sync_pump()`。

**C. 指令下发链（下行）**

```
平台 MQTT PUBLISH → 模组 → WIO1 → rx_cb → 0x52
  → cloud_iot_receive（分片重组，失败即丢整包不重排）
  → iot_onenet_downlink：方法分发
       ├─ 属性设置：bind_status / store_policy / upload_policy → 校验 → 落盘/生效 → 回 set_reply
       ├─ 属性查询：id → 取真实值（电量/充电/录音/容量/IMEI） → 回 get_reply
       └─ 服务调用：start/stop/mark/pause/resume record → 执行 → 回带 msg_id 的应答
  → cloud_4g_send → 0x50 → 平台
```

> 注意：代码里有暂停/恢复分支，**不等于**这些服务已在实机验收。

### 2.3 两级 FSM 的边界（迁移时必须保留的设计）

| | L4 链路 FSM（12 态） | L5 业务 FSM（7 态 T0–T6） |
|---|---|---|
| 回答什么 | 链路可用吗？下一步发什么控制命令？ | 业务该干什么？（订阅/上报/传文件/挂起） |
| 驱动 | 10 ms timer，主线程 | 1 s timer，`BIZ_RUN` 时由 4G tick 父机驱动子机 |
| 耦合 | `cloud_4g_is_mqtt_up()` 读、`state_cb` 边沿、`s_child_step_fn` tick | 同左 |

### 3.2 两套参考的关键差异

| 问题 | ZS302A | CAT1 sample | 对你的目标意味着 |
|---|---|---|---|
| 谁理解 `/multipart/init` 的字段 | 主控 | **模组** | 目标=模组（503） |
| 谁算 HMAC 签名 | 主控 | **模组** | 目标=503 |
| 谁判 `00000 / SYNC_SUCCESS` | 主控 | **模组** | 目标=503 |
| 谁持有 uploadUrl / objectKey | 主控 | **模组** | 目标=503 |
| 谁暂停 MQTT 避免与 PUT 抢链路 | 不暂停（两条物理链路） | **模组暂停+恢复** | 503 单模组必须处理 |
| 文件字节从哪来 | 主控本地 SD | 主控经 SPI 提供 | 目标=ATS 提供、503 消费 |

**结论：503 要做的不是"发明一套"，而是把 CAT1 的会话/签名/判定 + ZS302A 的物模型字段/规则合到一起。**

## 4. 目标职责划分（服务器下发全部由 503 处理）

```mermaid
flowchart LR
    S["云平台<br/>MQTT 物模型 + 云存 HTTP"]
    U["UMA503：协议解析 · 校验 · 签名 · 业务状态机 · 幂等 · 上报"]
    A["ATS3085E：录音 · 文件 · 界面 · 硬件状态"]
    S <-->|"MQTT / HTTPS"| U
    U <-->|"SPI：业务动作 · 文件块 · 执行结果"| A
```

| 能力 | 归属 | 说明 |
|---|---|---|
| 注网、DNS、TCP、TLS、HTTP、MQTT | 503 | 已具备 |
| 云端消息解析/校验/去重/回执 | **503** | 现状几乎空白（仅 bind_status） |
| 请求签名、init/分片/complete 状态机 | **503** | 现由 3085 的 `p4_upload.c` 承担 |
| 设备真实状态（电量/充电/录音/容量） | ATS 采集 → 503 组装 | 需新增 SPI 状态查询 |
| 录音、落盘、文件读取 | ATS | 503 按 offset/len 要数据块 |
| 策略生效（store/upload_policy） | 503 判 → ATS 执行 | 需新增 SPI 动作指令 |
| 事件上报（file_sync 等） | 503 | 需新增 |

服务调用的完成判定必须分三层，不能混：

| 层级 | 判据 | 现有证据能证明吗 |
|---|---|---|
| 消息到达 | MQTT 收到、SPI 送达 | 能（SPI CRC + 序号） |
| 动作执行 | ATS 回"已开始录音/失败原因" | 不能（未实现） |
| 业务应答 | 按服务器协议回 msg_id + 结果 | 不能（未实现） |

### 5.2 当前 PASS 不能证明的五件事

| 已有证据 | 能证明 | 不能证明 |

### 6.1 建议新增的最小 SPI 业务命令（不照抄 HTTP 语义）

| 命令 | 方向 | 载荷 | 语义要点 |
|---|---|---|---|
| `BIZ_ACTION` | 503 → ATS | action(start/stop/mark/pause/resume) + 参数 + msg_id | ATS 只执行，不做协议判断 |
| `BIZ_ACTION_RESULT` | ATS → 503 | msg_id + 结果码 + 文件 ID/开始时间/失败原因 | 用于生成合规应答 |
| `STATE_GET / STATE_RSP` | 双向 | 属性 ID 列表 / 值列表 | 查询应答必须取真实值 |
| `FILE_INFO / FILE_BLOCK` | 503 请求 → ATS 应答 | localFileId + offset + len | 503 不复制整份文件 |
| `EVENT` | 双向 | 事件类型 + 载荷 | file_sync、录音开始/结束 |
| `POLICY_APPLY` | 503 → ATS | store_policy / upload_policy | 保证"回执成功"与"行为生效"一致 |

## 7. 风险与待确认

| 项 | 现状/风险 | 建议 |
|---|---|---|
| 514 B 帧上限 | ZS302A 因 440 B 预签名 URL + 80 B 头超限，cJSON 组包失败、PUT 从未发出 | 503 直接持有 URL（不过 SPI），此坑消失；但 SPI 回传长 JSON 仍需分页（现为 16 KiB 扩展响应） |
| MQTT 与 PUT 抢链路 | CAT1 选择上传期间断开 MQTT，收尾恢复；ZS302A 两条物理链路无此问题 | 503 单模组必须显式选择并写成状态机分支 |
| 时区口径 | ZS302A 踩过 `+8` 重复偏移，audio_id 多 8 小时导致路径 miss | 全局只认"本地时间当 epoch"这一种口径，写入文档 |
| 文件指纹 | 采样 MD5 仅 200 B + 长度，不是完整性证明 | 保留 ATS 的 SHA256 作为内部校验，云端仍用采样 MD5 |
| 录音格式 | ZS302A 用 `.msbc`，P4 用 `.m4a` | 定一个 canonical 格式，否则 init 的 `audioFormat/contentType` 会不一致 |
| 503 存储 | 未确认文件系统/剩余空间；若要缓存待传队列必须确认 | 先做"ATS 持有文件、503 只读块"，避免 503 落盘 |
| 4G 侧 OTA | 两工程都未实现；CAT1 有完整 0x80–0x87 MCU OTA 可参考 | 单独立项，不混进本轮迁移 |
| 503 内 CP 栈修订 | P4 文档注明"CP 栈修订属特定镜像，换版本仍需复验" | 每次换镜像重跑 P4 |

## 8. 建议的推进顺序

1. **闭环一条下行**：bind_status 从"503 本地保存成功"推进到"503 校验 → 落盘 → 通知 ATS 生效 → 平台收到正确结果"。这是最小可验证的业务闭环，能一次性把"业务语义 + ACTION + 结果回传"打通。
2. **再做属性查询与策略**：把 `STATE_GET` 接上真实值，让 get_reply 不再是缓存镜像；store/upload_policy 落到 ATS 行为。
3. **最后迁上传状态机**：init/分片/重试/complete/file_sync 整体搬到 503，ATS 只保留"文件信息 + 指定范围字节"。此时才能说"服务器下发与上传响应全部由 503 处理"。

每步的验收都按三层判据写（收到 / 送达 / 执行并回包），否则会重演"PASS 了但业务没迁"的现状。
