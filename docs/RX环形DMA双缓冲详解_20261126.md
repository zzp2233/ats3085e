# RX 环形 DMA 为什么是 1024 分两半

> 对应代码：`D:\ats3085e\TAG_ZS3085E_241230\zephyr\drivers\spi\spi_acts_spi2_circular.h`
> 涉及函数：`spi_acts_spi2_circular_open`、`spi_acts_spi2_circular_transfer`
> 配套阅读：`ATS3085E与UMA503_从STM32到联网开发学习路线.md` 第 3 周

---

## 0. 一句话

**用 1024 字节切成 A、B 两个 512 字节的槽，硬件写满一个槽就自动绕回开头，让 DMA 和 CPU 永远在不同槽上工作，谁也不覆盖谁。**

---

## 1. 为什么必须是“环形”

SPI 主机一旦拉低片选、开放 TX 请求，时钟就会**连续不停地产生**——这是硬件行为，没有“暂停”这个选项。主机发 512 字节 = 512 个字节 = 4096 个时钟周期，中途不能停。

这意味着 RX DMA 也必须**连续不停地有地方写**。两种设计对比：

```
方案一：单块缓冲（写满就停）
DMA:  [写 512B] → 停 → 等软件重新配置 → 再写
                  ↑
            中间时钟照走，数据全丢

方案二：环形缓冲（写满自动绕回）
DMA:  [写满 1024B] → 硬件自动重载指针 → 接着写
                    ↑
              不需要软件干预
```

代码里打开这个能力的就一行（`:124`）：

```c
block.dest_reload_en = 1;   /* 到达环末端时让硬件重新装载目的地址和计数 */
```

对应通道控制寄存器第 18 位（`:9`）：

```c
#define SPI2_CIRC_RELOAD (1u << 18)   /* 通道控制字第 18 位表示重载使能 */
```

而且这个位不是“设完就算”——`open` 里还要**从硬件回读确认**（`:134`）：

```c
if (!(sys_read32(SPI2_DMA_REG(spi2_circ.rxch, 0)) & SPI2_CIRC_RELOAD)) {
    ret = -EIO; goto fail;   /* 重载未生效时禁止以循环模式运行 */
}
```

**为什么要回读**：如果重载位没真生效，DMA 会在 1024 字节后停住，而 SPI 时钟继续跑，后面的数据全部丢在 FIFO 里溢出——这种故障不报错，只表现为“块数不对”。所以必须在开始前验一遍。

## 2. 物理布局：1024 = 2 × 512

```c
#define SPI2_CIRC_BYTES 512u                        /* 每次片选传输的有效负载 512 字节 */
#define SPI2_CIRC_RING_BYTES (2u * SPI2_CIRC_BYTES) /* 接收区含两个等长槽 */
```

```
一块连续 SRAM（1024 字节，`spi2_dma_rx`）
┌───────────────────────────────┬───────────────────────────────┐
│          槽 0（A）            │          槽 1（B）            │
│   偏移   0 ～ 511（512 字节）  │  偏移 512 ～ 1023（512 字节）  │
└───────────────────────────────┴───────────────────────────────┘
  ▲                               ▲
  │                               │
even block（blocks&1==0）      odd block（blocks&1==1）
```

为什么要正好 512？因为**一笔 SPI 事务就是 512 字节**（`SPI2_CIRC_BYTES`）。一个槽正好装一笔，不多不少。

打开时还会填哨兵（`:114`）：

```c
memset(spi2_dma_rx, 0xa5, SPI2_CIRC_RING_BYTES);   /* 原始缓冲填入哨兵 */
```

**用途**：如果调试时看到某块区域还是 `0xa5`，说明**那里从没被 DMA 写过**——一眼就能区分“数据是 0”和“根本没写”。

## 3. 事件地图：两个槽对应两种中断

这是最容易搞混的地方。DMA 有两个“写满”事件，分别对应两个槽：

| 槽 | blocks 奇偶 | 事件 | 寄存器位 | 触发时机 |
|---|---|---|---|---|
| **槽 0（A）** | 偶数（blocks & 1 == 0） | **半传输 HF**（Half Transfer） | `1 << (16 + rxch)` | 写到 512 字节时 |
| **槽 1（B）** | 奇数（blocks & 1 == 1） | **传输完成 TC**（Transfer Complete） | `1 << rxch` | 写到 1024 字节时 |

代码（`:175-177`）：

```c
slot = spi2_circ.blocks & 1u;                                        /* 偶数块写前槽，奇数块写后槽 */
mask = (1u << spi2_circ.rxch) | (1u << (16u + spi2_circ.rxch));      /* 只筛本通道的 TC 和 HF 位 */
expected = 1u << (spi2_circ.rxch + (slot ? 0u : 16u));               /* 前槽应出现半传输，后槽应出现完成 */
```

**读法**：`slot ? 0 : 16` —— 前槽（slot=0）时移位 16（HF 位），后槽（slot=1）时不移位（TC 位）。

**为什么要区分两种事件**：因为“块序必须严格交替”。如果第 3 笔本该出 HF，结果读到了 TC，说明**中间漏掉了一整块**——立刻判 `-EIO`（`:218`）：

```c
if ((status & SPI_STATUS_ERR_MASK) || (pending & ~expected)) {
    stage = "RX_STATE"; ret = -EIO; break;   /* 来自另一个槽的事件都意味着边界失配 */
}
```

这一行是整个驱动的“错位检测器”。

## 4. 四笔数据的完整循环

```
时间 ─────────────────────────────────────────────────────────►

        第1笔(512B)       第2笔(512B)       第3笔(512B)       第4笔
             │                 │                 │              │
             ▼                 ▼                 ▼              ▼
       ┌───────────┐     ┌───────────┐     ┌───────────┐
  A    │  写入中   │     │  CPU 读   │     │  覆盖写   │
槽0    │  blocks=0 │     │           │     │ blocks=2  │
       ├───────────┤     ├───────────┤     ├───────────┤
  B    │   空闲    │     │  写入中   │     │  CPU 读   │
槽1    │           │     │ blocks=1  │     │           │
       └───────────┘     └───────────┘     └───────────┘

事件：    ⚡HF              ⚡TC              ⚡HF
         (A 满 512)        (B 满 1024)       (A 又满)
                           + RELOAD
                           指针回 0
```

关键点：**第 2 笔写完时，指针已经 RELOAD 回 A 开头了**，但第 3 笔还没开始——这段空档就是 CPU 读 A 的时间窗。

## 5. 逐笔状态表（含代码真正用来判定的量）

| 时刻 | blocks | slot | DMA 写指针 | RX 剩余计数 `remaining` | 期望事件 `expected` | CPU 该做什么 |
|---|---|---|---|---|---|---|
| 起始 | 0 | 0 | 偏移 0 | 1024 | HF（bit16+ch） | 等第 1 笔 |
| 第 1 笔完成 | 0→1 | 0 | 偏移 512 | **512** | HF | 复制槽 0 的 512B |
| 第 2 笔进行中 | 1 | 1 | 偏移 512→1024 | 512→0 | TC（bit ch） | 处理槽 0 |
| 第 2 笔完成 | 1→2 | 1 | **RELOAD 回 0** | **1024**（被重装） | TC | 复制槽 1 的 512B |
| 第 3 笔进行中 | 2 | 0 | 偏移 0→512 | 1024→512 | HF | 处理槽 1 |
| 第 3 笔完成 | 2→3 | 0 | 偏移 512 | **512** | HF | 复制槽 0（新一轮） |

**注意 `remaining` 那一列**——它是代码里判定“这一块真的完成了吗”的核心依据（`:237`）：

```c
remaining == (slot ? SPI2_CIRC_RING_BYTES : SPI2_CIRC_BYTES)
```

翻译成人话：

- 前槽（slot=0）完成时，剩余计数必须是 **512**（前面已写满一半）
- 后槽（slot=1）完成时，剩余计数必须是 **1024**（已经 RELOAD 重装过）

**如果 slot=1 但 remaining 是 0，说明 RELOAD 没发生** → 判失败。这一条比“看到中断”可靠得多，因为中断可能被误清或残留。

## 6. 三个术语

### 6.1 半传输事件 HF

DMA 总计数 1024，写到 512（正好一半）时硬件锁存一个标志。

**物理含义**：已经移完 4096 个 SPI 时钟，槽 0 装满了。

### 6.2 传输完成 TC

写到 1024 时锁存另一个标志。

**物理含义**：槽 1 也满了，整个环转了一圈。

### 6.3 RELOAD（重载）

TC 之后硬件**自动**做两件事：

```
目的地址：1024 → 回到起点
剩余计数：0 → 重装为 1024
```

**你代码里为什么特别强调“剩余计数回到 1024”**：因为这是判断“RELOAD 是否真的发生了”的唯一证据。地址指针软件看不见，计数可读。

代码在重载瞬间还留了一个 20µs 的宽容窗口（`:8`、`:224-233`），因为重载过程中 DMA 的 START 位会短暂掉一下：

```c
if (!checking_reload && slot && !txrem &&
    (remaining <= SPI_DMA_STRANFER_MIN_LEN ||
     (pending == expected && remaining == SPI2_CIRC_RING_BYTES))) {
    checking_reload = true;                 /* 仅后槽、TX 耗尽、计数接近零或已重载 */
    reload_start = now;
}
```

**为什么只在后槽允许**：只有后槽（环尾）才会触发重载。前槽如果 START 掉了，那是真故障。

## 7. 最费解的一句：“等真的产生新数据才开始覆盖”

RELOAD 之后，指针在 A 开头，但 DMA **不会主动写**。它在等：

```
RELOAD（TC 事件）
     ↓
指针回 A 开头，计数 1024
     ↓
DMA 静默等待
     ↓
第 3 笔片选拉低 → 第一个字节进 rxdat → 请求信号 → DMA 才开始写 A
```

所以“指针回到 A 开头” ≠ “A 已被覆盖”。窗口是这样的：

```
TC事件                              第3笔开始写A
  │                                      │
  ▼                                      ▼
──┼──────────────────────────────────────┼──────►
  │←────────── CPU 的时间预算 ──────────→│
     必须在这段时间里把槽 1（B）复制走
```

**风险**：如果 CPU 在这段窗口内没复制完，第 3 笔就开始覆盖。表现是：

- 数据不报错，但内容错位
- 因为 CRC32 校验的是“后写进来的那版”，**校验能通过，内容却是错的**

这是整个设计里唯一一个“静默错误”风险点。所以必须靠 READY 令牌保证节奏：**主机只有在 CPU 确认处理完上一个槽之后，才被允许发下一笔**。

## 8. 代码怎么判“这一块真的完成了”

`transfer` 的完成判据是**五个条件同时成立**（`:236-238`）：

```c
if (rxrun && !ts.busy && pending == expected &&
    remaining == (slot ? SPI2_CIRC_RING_BYTES : SPI2_CIRC_BYTES) &&
    !(status & SPI_STATUS_BUSY) && (status & SPI_STATUS_TX_EMPTY)) {
```

拆开：

| 条件 | 含义 | 不满足说明什么 |
|---|---|---|
| `rxrun` | RX 通道还活着 | 环形停了（真故障，非重载宽限） |
| `!ts.busy` | TX 通道已停 | 多发或少发 |
| `pending == expected` | 事件位是这个槽该有的 | 块序错位、漏块 |
| `remaining == 512 或 1024` | 计数落在正确位置 | RELOAD 没发生 / 写少写多 |
| `!SPI_STATUS_BUSY` + `TX_EMPTY` | 线端空闲 | 时钟还没走完 |

**为什么要五个一起看**：任何单独一个都可能被误判。比如“看到 TC 中断”不代表真的写满了 1024——可能前面漏了。五个一起看才闭环。

还有一条后面才查的（`:239`）：

```c
if (!(status & SPI_STATUS_RX_EMPTY)) { stage = "RX_FIFO"; ret = -EIO; }
```

**完成点上 RX FIFO 必须为空**——否则还有字节卡在 FIFO 里没进环缓冲，说明这一块少算了。

## 9. 为什么 RX 只启动一次，TX 每块重启

这是这张图里最反直觉的设计。

| | RX 通道 | TX 通道 |
|---|---|---|
| 启动次数 | **open 时启动 1 次**（`:140`） | **每块启动 1 次**（`:202`） |
| 目的地址 | 固定指向 1024 环，靠 RELOAD 绕圈 | 每块指向新的 512 字节 |
| 重载 | `dest_reload_en = 1` | **必须为 0**，否则会多发 |
| 谁封顶 | — | **TX 的 512 字节封顶时钟数** |

代码（`:194-199`）：

```c
spi2_dma_config_channel(..., spi2_circ.txch, true, SPI2_CIRC_BYTES);   /* 每块重配 512 */
if (sys_read32(SPI2_DMA_REG(spi2_circ.txch, 0)) & SPI2_CIRC_RELOAD) {
    ret = -EIO;   /* 若误开 TX 重载，将可能产生超出块长的时钟 */
}
```

**核心逻辑**：SPI 时钟数由 TX 决定。TX 每块只给 512 字节，时钟就只有 512×8 个，RX 正好填满一个槽。如果 TX 也开了重载，时钟会一直跑到 1024、2048…… RX 就会多写，直接越过槽边界。

**这是“用 TX 长度约束时钟数，用时钟数约束 RX 长度”的闭环。**

## 10. 三套 DMA 组织方式对照

“工单”（描述符 / command）是通用概念，三个平台用三种不同的方式组织它。

| | STM32（F1/F4 传统 DMA） | 3085E（acts PDMA） | 503（ARM PL080 链表） |
|---|---|---|---|
| 一次配置搬多少 | 一条，由 `CNDTR` 计数 | 一条 block config | 一张描述符 |
| 多条怎么组织 | CPU 反复重配，或 `DMA_Mode_Circular` 绕圈 | `dest_reload_en = 1` 绕圈 | 描述符里 `next` 串成链 |
| 谁推进 | CPU，或硬件重装计数 | 硬件重装计数 + 地址 | 硬件顺着 `next` 自己取下一张 |
| N 块需要 CPU 介入 | **N 次** | 1 次 | **1 次**（写完整条链） |
| 能表达不均匀任务 | 不能 | 不能 | **能**（每张工单长度/方向/增减都可不同） |

### 10.1 三种写法对照

```c
/* STM32：一条拖到底，靠模式位决定传完干什么 */
DMA_InitStructure.DMA_BufferSize = 7;
DMA_InitStructure.DMA_Mode       = DMA_Mode_Circular;   /* 传完自动重装计数 */

/* 3085E：一张 block config + 重载位 */
block.block_size    = SPI2_CIRC_RING_BYTES;             /* 1024 */
block.dest_reload_en = 1;                               /* 环尾自动重装 */
dma_config(dev, ch, &dc);                               /* dc.head_block = &block */

/* 503：多张工单用 next 串链，只交首地址 */
desc[0].next = (uint32_t)&desc[1];
desc[1].next = (uint32_t)&desc[2];
desc[n-1].next = 0;                                     /* 0 表示链结束 */
lc_load(&desc[0]);                                      /* 写进 DDADR，硬件自己走 */
```

### 10.2 为什么 503 必须用链表

因为它的工单是**不均匀**的：RX 是“外设固定地址 → RAM 递增”，TX 是“RAM 递增 → 外设固定地址”，两边的方向、地址增减规则完全相反（见你那张 5.503 表格）。

环形结构只能表达“同样的一块反复做”，表达不了“这张和那张规则不同”。链表天生能表达——**每张工单自带完整规则**。

## 11. 从零认识 cache 一致性

这一节是基础。第一次接触 cache 的人从这里开始，已经理解的人可以直接跳到第 12 节看本项目的具体做法。

### 11.1 为什么会有 cache

CPU 和内存的速度差得离谱：

| 谁 | 典型延迟 |
|---|---|
| CPU 执行一条指令 | 1 个周期 |
| 访问片上 SRAM | 1～3 个周期 |
| 访问外部 DDR | **100～300 个周期** |

如果每次读变量都去 DDR，性能会掉一到两个数量级。所以中间加一层**又小又快**的缓存：

```
     CPU              Cache              内存(DDR)
   (200MHz)      (几KB~几十KB)          (几百MB)
      │                │                    │
      │ 读 ──────────► │  命中 → 1~4 周期    │
      │                │  未命中 → 去内存 ──►│
      │                │◄──── 搬一整行 ──────│
```

**搬运单位不是 1 字节，而是一整行**（cache line，通常 32 或 64 字节）。因为“既然跑一趟，就多拿点”。

### 11.2 问题怎么产生：一个用缓存，一个不用

```
     CPU ──► Cache ──► 内存 ◄── DMA
            (走缓存)           (不走缓存，只看内存)
```

DMA 是独立通道，**不参与 CPU 的 cache 体系**。它眼里只有物理内存。于是：

- CPU 看到的是 **cache 里的副本**
- DMA 看到的是 **内存里的原件**

**两份可能不一样。** 这就是“cache 一致性”的全部含义。

### 11.3 发送方向：CPU 写，DMA 读

```
t0   CPU 写 buf[0] = 0x8C
       │
       └─► 只写进了 cache，标成"脏"（dirty：cache 比内存新）
           内存里还是旧值 0x00

t1   CPU 启动 DMA 发送

t2   DMA 读内存 → 拿到 0x00 → 把 0x00 发出去
```

**后果**：你写了 0x8C，对方收到 0x00，**且不报任何错**。

**正确的做法是 clean**：

```
clean = 把 cache 里的脏行写回内存
        （"我把最新的值交上去了"）
```

### 11.4 接收方向：DMA 写，CPU 读

```
t0   DMA 把收到的数据写进内存 buf = 0xAB

t1   CPU 读 buf
       │
       └─► 先查 cache → 命中了！
           cache 里是之前读过的旧副本 0x00
           → 返回 0x00（错！）
```

**后果**：DMA 明明写进去了，CPU 读到旧值。

**正确的做法是 invalidate**：

```
invalidate = 把 cache 里对应的行作废
             （"我这份副本不要了，下次去内存拿真值"）
```

### 11.5 三个术语

| 术语 | 含义 | 类比 |
|---|---|---|
| **dirty（脏）** | cache 里的值比内存新，还没同步 | 草稿改了但没交上去 |
| **clean（写回）** | 把脏行同步到内存 | 把草稿交上去 |
| **invalidate（作废）** | 丢掉 cache 副本，强制下次读内存 | 把过期草稿撕了 |

### 11.6 三种解法

| 解法 | 做法 | 代价 | 谁在用 |
|---|---|---|---|
| **A. 放进不走 cache 的区域** | 缓冲放 TCM / 内部 SRAM / uncached 映射区 | 内存受限 | **3085E** |
| **B. 手动 clean / invalidate** | 每次传输前后调 API | 有开销、易漏 | **503** |
| **C. 硬件一致性** | SoC 有 cache 一致性互联 | 硬件成本高，MCU 少有 | 一般不用 |

A 最省事——问题在“选址”阶段就消掉了，运行时不用管。
B 最容易漏——忘了 clean 发错数据，忘了 invalidate 读旧数据。

### 11.7 为什么你在 STM32 上从没遇到过

**Cortex-M3/M4 没有 data cache。**

```
STM32F1/F4：CPU 写 → 直接写进内存
            DMA 读 → 读同一份内存
            → 永远一致
```

（F4 的 ART accelerator 只是 Flash 指令预取，不是 data cache；H7 的 L1 D-cache 才是同类东西，H7 上通常用 MPU 把 DMA 缓冲设成 non-cacheable。）

所以迁到带 cache 的核上，这是一块**必须新建的认知**，不是“换个寄存器名”那么简单。

### 11.8 隐藏的坑：cache line 粒度

这个坑比前两个更阴。cache line 是 32 或 64 字节，你只写了 2 个字节然后 clean：

```
cache line（32 字节）
┌──────┬──────┬────────────────────────┐
│ 0x8C │ 0x01 │   ... 剩下 30 字节 ...  │
└──────┴──────┴────────────────────────┘
   ↑ 你写的        ↑ cache 里是旧副本

clean 会把整行 32 字节写回内存
   ↓
若这行剩下 30 字节是 DMA 刚写的新数据
   → 被你的旧副本覆盖掉了
```

**对策**：DMA 缓冲按 cache line 对齐，且大小是 cache line 的整数倍。

本项目的 512 和 1024 正好是 32/64 的整数倍，所以相对安全——**但这是巧合，不是设计保证**。

## 12. cache 一致性：本项目两个平台的具体做法

原理见第 11 节。这一节只讲 3085E 和 503 各自怎么落地。

### 12.1 一句话回顾

**CPU 看 cache，DMA 看内存，两份可能不同。** 下面两个平台用两种方式让它们重新对齐。

### 12.2 3085E 的做法：从地址上掐掉问题

```c
/* :90 —— 启动前就要求缓冲位于内部 SRAM */
if (!spi2_dma_internal_ram(spi2_dma_tx, SPI2_CIRC_BYTES) ||
    !spi2_dma_internal_ram(spi2_dma_rx, SPI2_CIRC_RING_BYTES)) return -ENOTSUP;
```

内部 SRAM（紧耦合内存）通常**不经过 data cache**，所以根本不存在一致性问题。这是在“选地址”阶段就把问题消灭，比运行时反复 clean 便宜得多。

配合的两处屏障只负责**顺序**：

```c
/* :200 —— 启动 TX 之前 */
__asm__ volatile ("dmb" ::: "memory");   /* 排序内存写入和通道启动，确保 DMA 能看见发送数据 */

/* :253 —— 复制已完成槽之前 */
__asm__ volatile ("dmb" ::: "memory");   /* 在读取已完成槽前对内存与设备访问排序 */
```

这两条正好对应两个方向：

| 位置 | 方向 | 保证什么 |
|---|---|---|
| `:200` `dma_start(tx)` 之前 | CPU 写 → DMA 读 | TX 的数据真的落到内存才启动 |
| `:253` `memcpy` 之前 | DMA 写 → CPU 读 | 读到的是 DMA 刚写进去的最新值 |

### 12.3 503 的做法：clean + DSB

```c
/* 1. CPU 写完整条工单链 */
desc[i].source = ...; desc[i].target = ...; desc[i].next = ...;

/* 2. clean：把 cache 里的工单刷回内存 */
/*    DSB   ：等这些写操作真正完成 */
/* 3. lc_load()：把首地址写进 DDADR */
/* 4. 置 RUN */
```

503 没有“把缓冲放内部 SRAM”这条路（它要搬的目标就是普通内存），所以只能**运行时维护**：写前 clean，读前 invalidate。

### 12.4 一个必须分清的区别

| 手段 | 管什么 | 不管什么 |
|---|---|---|
| `DMB` / `DSB`（内存屏障） | **顺序**：保证前面的写先完成 | **不管可见性**：数据可能还在 cache |
| `clean` / `invalidate`（cache 维护） | **可见性**：让 DMA 看到内存里的真值 | 不管顺序 |

**两者不能互相替代。** 缓冲在 cache 区域时，光加屏障不够，必须 clean；反过来，只 clean 不保证顺序，也要屏障。

3085E 之所以只加 `dmb` 就够了，是因为它**先把缓冲放到了不走 cache 的内部 SRAM**——前提条件已经消掉了，剩下的只是顺序问题。

## 13. 失败了怎么看

驱动在每个阶段都给 `stage` 打标签（`:168`、`:193`、`:196`、`:201`、`:211` 等），失败时打三行：

```
SPI11 DMA fail rev=11a-wrap stage=RX_STATE ret=-5 block=7 slot=1
SPI11 DMA sample sta=... pending=... expect=... rxrem=... txrem=... rxrun=...
SPI11 DMA halted ctrl=... sta=... rxrun=... txrun=... rxrc=... txrc=...
```

`stage` 直接告诉你在哪一步挂的：

| stage | 含义 | 常见原因 |
|---|---|---|
| `PRECHECK` | 开始前的残留检查 | 上一次事件没清、片选没抬 |
| `TX_CONFIG` | 配 TX 通道 | 通道号错、DMA 忙 |
| `TX_MODE` | 检查 TX 重载位 | 误开了重载 |
| `TX_START` | 启动 TX | 通道状态异常 |
| `RX_STATE` | 事件与计数不符 | 块序错位、环停了 |
| `RX_FIFO` | 完成点上 FIFO 非空 | 少算字节 |
| `TX_COUNT` | TX 报停但计数非零 | 少发 |
| `TIMEOUT` | 超 100ms | 从机没回 READY / 线路问题 |

**排错顺序**：先看 `stage`，再看三行里的 `rxrem`/`txrem`/`rxrun`。`rxrem` 不对就是环形问题，`txrem` 不对就是发送长度问题。

## 14. 跟你已经学的“8 拍”对上

```
1 块 512 字节
= 512 × 8 拍
= 4096 个 SPI 时钟周期
= 512 次完整的 8 拍移位
= 512 次“SR 把接收字节交给 RDR”
```

所以 HF 事件（写到 512）的物理含义是**“4096 个时钟周期已经走完”**。TC 事件是 8192 个时钟。

`blocks` 计数就是“已经完成多少笔 512 字节事务”，`slot = blocks & 1` 就是“这笔该落哪个槽”。

## 15. 一页总结

```
为什么要环形    ：SPI 时钟连续不断，DMA 必须一直有地方写
为什么分两半    ：CPU 处理 A 时 DMA 写 B，永不撞车
两个事件       ：槽0→HF(bit16+ch)，槽1→TC(bit ch)
RELOAD         ：TC 后硬件自动回零，证据是“剩余计数回到 1024”
唯一风险       ：RELOAD 到第3笔开始之间的空窗，CPU 必须读完上一个槽
防风险手段     ：READY 令牌 + 五个条件同时判定 + 哨兵 0xa5
不对称设计     ：RX 启动一次靠重载绕圈，TX 每块重启用 512 封顶时钟
工单（描述符）  ：一张搬运任务，含源 / 目的 / next / 控制位
三平台组织     ：STM32 反复重配 · 3085 靠重载绕圈 · 503 靠 next 串链
cache 一致性   ：CPU 写 ≠ DMA 看得见；3085 用内部 RAM 规避，503 用 clean
```
